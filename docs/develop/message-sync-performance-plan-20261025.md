本文是待实施方案，不是修复完成或性能验收回执。范围包含新消息到达慢、QQ 已读后 WeQ 红点消失慢、进入会话慢、聊天界面卡顿四个现象；复用现有服务和状态，不重写整个消息系统。

- 已将新消息目标、仍有红点／高亮的会话接入快速未读校准，不等待聊天首屏或全目录扫描。

## 已确认机制与待测边界

| 范围 | 当前机制 | 判断边界 |
| --- | --- | --- |
| 聊天实时刷新 | `refreshWindow` 可同时发起多次读取，只接收最后启动的请求 | 运行真实回调的受控复现：8 次连续启动，旧响应逐次在新请求启动后返回，期间上屏 0 次，停止触发后上屏 1 次；不是日常延迟占比 |
| 变更传播 | 任意数据库通知刷新多个目录、当前消息窗口和未读，并将所有窗口缓存标脏 | 已确认调用关系，实际 SQL 次数、去重效果及占时待采样 |
| 实时差分 | 会话串行，单会话按 500 条一页读到追平后才通知 | 已确认队头阻塞条件；真实积压量和正文耗时待测 |
| 未读查询 | 基础水位读取后，继续等待排除自己发送序号的查询；一个批次全部完成才返回 | 已读会话可能等待同批其他会话的附加扫描；基础读取本身已批量化，不应误称逐会话查询 |
| 未读重试 | 一个批次任一目标失败会把整批放回队首，并对整个队列退避 | 存在失败会话反复挡住健康目标的条件；不是已经复现的日常故障结论 |
| 本地未读落盘 | `LocalUnreadStore.flush` 整体序列化并同步原子写入，包含文件和目录 fsync；新消息通知在观察落盘之后 | 已确认主进程阻塞入口，需测量持久化耗时，不能先归因为磁盘故障 |
| 首屏缓存 | 默认关闭的“从第一条未读开始阅读”同时控制窗口缓存恢复 | 普通阅读模式切回会话仍重查；优化必须保留打开最新消息的语义 |
| 消息页附加工作 | 引用逐条读取 40900、读取全会话撤回映射、关闭同库连接、再顺序查询漫游缓存 | 已确认路径；原生连接重开与同库排队成本需按实际产物测量 |
| 渲染与媒体 | 当前时间线全量渲染，翻页持续追加；媒体寻址使用同步目录扫描，缩图缺失会返回原图 | 已有 lazy/async 解码和部分资源预算，不能说完全没有优化；当前 loaded 不受缓存 200 条上限约束 |

## 不改变的正确性约束

1. 所有异步读取、订阅、缓存和重试绑定账号、数据目录身份和会话类型；设备保留 8／134，不并入好友水位 1。沿用现有临时私聊归一规则，不额外推断未确认类型。
2. QQ 到 WeQ 的已读同步是读取校准，不为消红点额外写 QQ 库、发送已读包或启用默认关闭的已读上报。
3. 缺少已读行、水位未知、查询失败、正文尚未落库不解释为已读或零未读；继续保留既有本地基线、明确入站和错误语义。
4. 自己发送、同步回声、历史导入和漫游补齐不制造未读；不得为了加速而直接用最新序号增长点亮红点。
5. 保留手动已读、手动未读、撤销和新到消息的现有优先级。已有回归明确要求：QQ 水位推进不会自动取消 WeQ 手动未读；这类红点不属于同步延迟。
6. 阅读仅推进本次捕获的固定目标，不能让重试顺带读掉后来到达的消息；高亮仅清除已确认范围内的条目。
7. 旧读取不能恢复已经确认消失的红点，也不能清除后来到达的新提醒；全量扫描没有覆盖的目标不因扫描结束而清零。
8. 历史／搜索窗口不被实时刷新拉回最新；分页、同序号灰条、64 位标识、阅读锚点和跨窗口选择保持原有契约。
9. 只读快照不写源库；需要写入的既有操作继续保留未知 BLOB 字段、比较更新和失败回执。
10. 保留本地已捕获未读的持久化语义，不以丢失未读、关动画、截断历史或提高堆上限换取性能数字。

## 目标链路

```text
QQ 本地落库
  -> 目录事件 / 文件轮询 / 前台有提醒目标的低频校准
  -> 快速水位读取与已知变更目标
      -> 已读状态校准与未读补查 -> 按目标更新角标
      -> 可见会话消息窗口的合并刷新 -> 增量映射与绘制
      -> 公平分页的正文差分 -> 明确实时入站、关键词等消费者
  -> 后台目录校准、历史补齐、分析与索引工作
```

新消息出现与 QQ 已读消点共用水位和一致性规则，但触发不能混为一谈：前者可能有新消息目标通知，后者常只有 48902 变化而没有最新序号增长。不得只监听 `onNewMessages` 来实现已读消点。当前文件事件不能直接说明变了哪张表，未知变化仍需受控校准，不能虚构精确的表级通知。

## 实施顺序

### S0：先建立可比较的运行基线

- 记录实际运行实例的主进程／preload／renderer 与原生产物身份、构建时间及监听能力。区分源码已提交、开发模块热更新、主进程已重启和安装版已替换。
- 复用现有脱敏诊断，记录事件发现、目标入队、SQL 排队／执行、引用补全、持久化、IPC、状态提交和绘制的分段耗时。应用层测到的总查询耗时不能冒称原生执行耗时；原生没有队列指标时单列未知。
- 统计队列长度、最老等待时间、在途数、丢弃响应数、每轮 SQL／返回条数、fallback 分区比例、长任务与消息 DOM 数。日志有界，不保存正文、UID、群号、路径、URL 或凭据；关联使用短期无业务含义的采样 ID。
- 同一个固定构建和场景比较改前改后，不用当前源码结果解释未更新的运行实例。先做只读采样，不以重启、GC 或清缓存改变现场。

### S1：统一修正实时调度，避免刷新饥饿

- 将 `refreshWindow` 接入现有刷新合并模式：同一会话窗口至多一个在途请求；期间通知仅设置 pending，完成后补一轮，不累计请求。
- 新的 dirty 通知不立即作废当前在途响应；仅来源／会话／阅读窗口改变、明确更新已经提交或阅读写入保护冲突时拒收。否则即使持续收消息，也应持续显示可用进展。
- 扩展现有未读队列，分开实时新目标、QQ 已读校准和后台全目录扫描，目标去重，成功结果逐批交付。首屏只让后台全量扫描让路，不阻塞快速角标校准。
- 对正文差分逐页通知并轮转会话，保存可靠游标及同序号边界；设置每轮工作预算，预算耗尽主动续作，不依赖下一次文件变化。失败目标独立重试。
- 将每次库变化的全目录刷新改为目标更新与受控全量校准。只修改对应缓存；未知变化可标全局校准版本，但不能立刻对所有窗口发查询。
- 队列容量和重试生命周期有界，溢出只合并变更并登记补扫需要，不静默丢失数据。保留固定窗口通知和 1 秒文件轮询。
- 调度优先级不能抢占已经执行中的原生 SQL。先缩短后台任务的单次查询并在批间让出；需要原生优先级或独立只读连接时另核实际接口和锁行为，不假设 JS 并发就能解决同库串行。

验收反例：连续变化和慢查询同时存在时仍周期性上屏；一个积压群或损坏目标不阻断另一个健康私聊；切走再切回同一会话不能接收旧窗口结果。

### S2：为 QQ 已读消点建立不受精确计数拖累的快路径

- 在现有批量水位 SQL 和 `LocalUnreadStore` 上拆出基础读取与必要附加计数，不再为一批会话等待全部 outgoing 序号扫描后才交付已确定结果。
- 有可信已读位置、最新水位可知且已覆盖，同时不存在范围外明确入站／高亮和手动未读覆盖的目标，可以立即按既有解析规则确认已读；不需要读取消息正文或枚举自己发送序号。
- 仍有未读、收发混合或信息不完整的会话继续使用精确计算。附加查询绑定基础读取区间和来源版本，期间水位变化按现有保护重新校准，不把不同时间的几份结果拼成确定的零值。
- 文件变化时优先校准实际持有红点或高亮的合法目标，并保留原 chatType；目标来源覆盖已加载最近会话及角标状态实际对应的真实会话，不只考虑视口内一页，也不将群助手聚合 ID 当作 QQ 会话。
- 新消息水位变化可以提前通知“目标需补查”，但这不是“收到一条入站”；缺 QQ 水位时，仍须等到真实正文差分确认对方消息才能记录本地未读。
- 对前台且仍有提醒的目标增加低成本、可停止的校准兜底，候选间隔 1 至 2 秒，按基线调优；没有提醒、窗口隐藏或账号关闭时停止该轮询。后台维持现有受控监听，返回前台立即校准。
- 失败仅退避对应目标，健康目标继续执行；返回完整性按请求目标校验，遗漏目标不能当成功。显式新证据可在限频内提前补查一次，不能被旧的 30 秒整队列退避拖住，也不能无限绕过退避。
- 新旧快照、手动操作与全量扫描继续共用版本保护。前台恢复、订阅重连或漏通知后做一次有限补扫；只有已读变化、没有新消息时也必须消点。
- 将每目标快照、计数和高亮作为一致补丁应用，只让变化行触发渲染；去除整份高亮对象的反复 JSON 序列化比较。

验收反例：仅推进 QQ 已读水位、最新 seq 不变；仅高亮清除；首屏失败或全量扫描持续阻塞；一个失败目标混在健康目标中；QQ 阅读期间又收到新消息；手动未读不得被清掉。

### S3：解除持久化与重复数据库读取的阻塞

- 测量 `observeNewMessages/getUnreadInfos -> local.flush` 中序列化及 fsync 成本。复用现有 JSON／原子写工具，改为单写者、版本化、可合并的异步原子落盘，不发起并行覆盖同一个状态文件。
- 必须持久化后才能确认的入口，等待自身状态版本真正发布后再确认或通知，不将“已排队写入”当成“已保存”。新版本到来时不让旧写入覆盖新状态；失败保留 dirty 和可重试状态，关闭／切号等待或显式处理未完成发布。
- 合并同源重复水位读取，成功快照只复用到已知有效版本；不要用较长 staleTime 掩盖已读变化，也不要改变已读上报开关或 SSO 回执语义。
- 引用缓存按一页消息 ID 批量读取；撤回标记只查当前页需要的记录或复用可失效映射。读取函数不再随意关闭共享的整库连接，账号关闭和写入释放行为分别核对。
- 漫游缓存复用现有三种来源、同一去重规则和序号验证，减少串行往返；优先合并查询或并行独立来源，不在 SSD 复制真实消息库。
- 降低年度索引、分析／导出与首屏的竞争：批量任务有公平让出，首次索引构建不因固定延迟到点就默认适合执行。库表及索引变更先用合成 SQLite 和 EXPLAIN 验证，UID 回退要有实际比例依据。

验收反例：异步写完成顺序颠倒、写失败、换号、关闭及重启恢复；同一页大量引用；撤回／删除标记变化；只读源；数据库尚无可选表；大 UID 回退分区。

### S4：缩短进入会话的关键路径

- 将窗口缓存复用与“从第一条未读开始阅读”偏好解耦。普通模式仅恢复最新窗口并后台校准；历史缓存不能作为普通模式的最终最新页，未读偏好保持原阅读锚点。
- 缓存命中先显示有界结果，保留 dirty／校准状态；无缓存时正文优先，非必要群资料、引用缩图等后补。撤回、删除等影响内容语义的标记应随正文提供，不能先展示应被隐藏的内容。
- 群首屏保留现有 25 条、普通分页保留 50 条作为起点，不靠进一步减少内容量掩盖查询成本。正文和附加来源正确合并后，任何请求失败、取消、窗口失效都结束自身加载态。
- 合并最近会话重复首批读取，全目录成员归属等必要后台加载继续分批完成，不删除完整目录能力；不在每次库变化重新预取全部分页。
- 复核导航切换时的缓存序列化和 DOM 阅读位置采集，避免在 React render 中执行较大 JSON 序列化或反复同步布局。缓存容量、原始媒体引用和既有保留策略不扩大。

验收反例：A-B-A 快切、缓存脏／过期、未读偏好开关、历史窗口切回、群资料迟到、首屏抛错、同时发生数据库变化和搜索定位。

### S5：修正渲染复杂度和媒体负载

- 为缺失引用预览一次性建立消息索引，保留发送者／时间约束以及多匹配不猜测的规则，目标复杂度从 O(引用数乘窗口消息数) 降至 O(消息数加引用数)。
- 合并消息窗口时复用未变化行引用；模板映射按真实消息身份及内容／装扮／成员版本增量计算。稳定 props 后再加行级 memo，不能只包 memo 而继续重建所有参数。
- `file_search` 改异步目录读取、共享目录快照及有界正／负缓存，mtime／新下载可失效；合并同媒体的缩图和原图查找。失败不串图，不对缺图无限扫描月份。
- 复用现有缩图模块，气泡缺少 QQ 缩略图时生成实际尺寸受限的预览；灯箱保留原图。遵守 GIF／APNG 与动画表情的既有播放语义，不能把所有动画默认变静态。
- 保留已有装扮帧／字体预算和隐藏页暂停机制，补查普通聊天媒体的离屏释放、全量加载中的节点和图片像素峰值；不将受管预算冒称 Chromium 总内存硬限制。
- 在上述改动稳定后接入动态高度虚拟时间线。先核对已安装依赖与现有侧栏虚拟列表能力，确实不足才选必要的成熟库，不从头实现滚动引擎。逻辑消息窗口／选择快照与 DOM 窗口分离，不能把“未渲染”等同于“未加载／未选择”。
- 虚拟化覆盖灰条、时间分隔、缺口、多选／框选、搜索、日历、图片加载后高度变化、复制导出和滚动锚点；不通过强制裁掉历史或卸载整个聊天页规避问题。

验收反例：两千条引用、反复编辑一条消息、连续新增、长图与坏图、图片解码高度变化、混合装扮、数千条已加载历史以及跨虚拟窗口选择。

单测不碰真实 QQ 数据、不联网。复用 `@weq/testkit` 明文 SQLite 夹具，针对实际源码路径添加失败回归，不用纯字符串断言替代调度、SQL 和组件行为。

| 测试层 | 必须覆盖 | 验收口径 |
| --- | --- | --- |
| 调度器 | 连续通知、慢响应、失败、销毁、账号切换、积压轮转 | 消息刷新同窗至多 1 个在途；持续输入仍交付；队列不无限增长 |
| SQLite 水位与计数 | 最新 seq 不变但已读推进，缺水位，空／坏 BLOB，同批混合已读和大量自己发送 | 正确目标能先完成；错误和未知不自动清零；附加查询数量和返回量有断言 |
| 本地状态 | 自己发送、收发混排、设备回声、历史导入、手动未读／撤销、旧快照回流 | 已有语义与持久化恢复全部保留 |
| 异步持久化 | 新旧版本交错、失败重试、切号、正常退出、未成功发布 | 已确认保存的状态能恢复；旧写不覆盖新写；无静默丢失 |
| 真实组件 | 首屏慢／失败，隐藏页恢复，只有高亮，群助手聚合，导航快切 | 红点／高亮一致，加载必收尾，旧会话不污染当前页 |
| 性能合成场景 | 5000 会话、多个忙群、500／2000 条引用、数千条历史、媒体批量失效 | 操作次数与在途数先过结构性预算，再比较同构建硬件下耗时 |
| 视觉与交互 | 桌面／窄屏、浅／深色、自定义强调色、背景、减少动态效果 | 无错位／重叠，消息锚点稳定，键盘／多选／拖选与灯箱正常 |
| 桌面 QQ 实测 | 私聊／群聊的新消息、仅 QQ 阅读、读到一半又来新消息、QQ 暂未写库、自己发送、恢复焦点 | QQ 落库与界面更新分别取证，不把用户点击时刻假设为落库时刻 |
| Web／Remote | 共享 API 的通知、断线重连、来源隔离和前后台恢复 | 不重复整库扫描；不改独立手机仓库或扩大配对权限 |
| 长时间运行 | 固定产物、多轮切会话／媒体／隐藏恢复，观察至少 1 小时再决定是否延长 | 无队列／DOM／内存单调无界增长；仅作观测，不自动 GC／重启 |

候选性能目标须在 S0 固定机器、构建、数据量和负载后确认，不是当前成绩：

- 正常负载的事件快路径，已确认 QQ 本地落库到角标绘制 P95 不高于 1 秒；仅使用兜底校准的场景单列，候选不高于 3 秒。
- QQ 尚未落库的等待单独报告，不能要求 WeQ 提前推断已读。长原生 SQL 已在执行的等待也单独报告，但不能从总端到端指标中隐藏。
- 缓存命中切换的消息首帧候选 P95 不高于 150ms；冷首屏先记录基线，再以减少关键路径查询和显著改善 P95 为验收，不预先承诺所有大库绝对耗时。
- 所有场景报告样本数、P50／P95／最大值、错误／重试数和峰值在途量；小样本直接列原始分布，不用单个最好结果宣称改善。
- 时间线 DOM 随视口而不是已加载消息总量增长；缺失引用的查找次数应近线性。滚动与输入检查长任务分布，不只看平均帧率。

每批只提交本任务已确认改动，保持当前分支和其他任务现场，不自动推送。方案不是必须一次性落地的跨包大改；前一批的测量结果可以缩小后续范围。分支隔离若涉及大规模重构，按本机及仓库现行约定处理。

用户可感知修复按同一事件归并到 Unreleased，不把调试过程拆成许多更新条目。类型、接口及文档同步；按影响范围运行专项测试，不默认全仓 CI。修改打包链路才补实际打包验收。

运行交付分别记录源码提交、构建产物、实例是否加载和真实业务验收。主进程／preload 变更不靠 renderer 热更新冒称生效；需要打包或重启时正常交付并核验，不擅自终止日常应用或在途业务。
