# QQ 秀协议逆向（2026-10-31）

> 本文基于 2026-10-31 的一组 Android 真机 SSO 抓包（TXHook 导出），覆盖四条 QQ 秀 OIDB
> 与一条「QQ 秀专有表情」的发送。**未改动任何仓库代码**；本文只记录字段布局、编号规则与
> 实测结论。
>
> 抓包里出现的 uin / uid / 资源 hash / 图片 URL 一律用占位符表示（`<uin>`、`<peer_uin>`、
> `<hash>`、`<uid>`），真实值不入库。

## 一、抓包总览

| 文件 | 命令 | 方向 | 用途 |
| --- | --- | --- | --- |
| 自己的 QQ 秀 | `OidbSvcTrpcTcp.0x9b02_0` | 请求 / 响应 | 查**自己**的形象：分类树 + 各分类预览图 |
| 他人的 QQ 秀 | `OidbSvcTrpcTcp.0x9572` | 请求 / 响应 | 查**指定 uin** 的穿戴部位 + 三档全身像 URL |
| 商城套装 | `OidbSvcTrpcTcp.0x9dbb_0` | 请求 / 响应 | 拉商场分类树 + 各分类下的套装/单品 |
| 衣柜列表 | `OidbSvcTrpcTcp.0x9578_0` | 请求 / 响应 ×2 | 按「已拥有槽位 + 分类」拉商品列表，分页 |
| QQ 秀表情 | `MessageSvc.PbSendMsg` | 请求 / 响应 ×3 | 私聊发一条图片型表情（含互动表情包） |
| 表情目录 | `OidbSvcTrpcTcp.0x957b_0` | 请求 / 响应 | 拉全部 48 个互动表情包定义 |

全部请求走同一套 `OidbSvcTrpcTcp` trpc 信封；表情走普通消息发送通道。

## 二、通用信封

四条 OIDB 的信封完全同构（native 侧 `sendOidbPacket` 组的就是这一层）：

```
field 1  uint32   命令号（如 0x9b02 = 39682）—— 信封里回填一次
field 2  uint32   subCommand（这四条都是 0）
field 3  uint32   reserved（UIN-form 变体为 1；这四条抓包里都是 0）
field 4  bytes    **业务 body**（下文各命令的字段都在这一层里）
field 6  string   平台串，恒为 "android <版本>"（如 "android 9.3.75"）
```

`field 4` 里第一项恒为客户端信息，四条命令都是同一形状：

```
1 {
  1 { 1: "9.3.75" 3: 109 }   ← 客户端版本 + 一个常量 109（未解，四条命令一致）
  3: 2                       ← 平台标记（Android=2）
}
```

> 只有 `0x9572` 的版本串是四段式 `9.3.75.42350`，其余是 `9.3.75`。看起来是随请求类型
> 取的两种版本格式，不像是校验项 —— 实测把 PC 端版本塞进去也一样被拒（见第九节）。

抓包导出文件在 payload 前多带 4 字节大端长度前缀（等于头部 `size=`），解析时先剥掉。

## 三、`0x9b02_0` — 查自己的 QQ 秀

请求 body（剥前缀后 42 字节）只带客户端信息，**没有 uin**（身份来自会话）：

```
1 { 1 { 1: "9.3.75" 3: 109 } 3: 2 }
```

响应 body：

```
1 { 1 { 1: "9.3.75" 3: 109 } 3: 2 }   ← 版本回显
2 {                                    ← 分类项（字段 2 重复出现）
  1: 分类 id
  2: 分类名
  4: 子分类（递归，结构同本项）
  5: 1            ← 可见/启用
  6: 1            ← 有子项？只有「动作」是 1
  7: 3 或 4       ← 3 = 一级分类，4 = 部位分类
  8: 分类预览图 URL（qqshow.gtimg.com 的 72×72 PNG）
}
```

本次抓包解出的分类树（与 `0x9dbb` 的分类树同构，只是那里多了 `20000 全部` /
`20008 全部` 两个聚合节点）：

```
10    角色          (预览图)
10003 形象          (预览图)
      1    套装
      5    上装
      6    下装
      7    鞋子
      2    发型
      8    配饰
            8003 头饰   8005 脸饰   8014 肩饰   8021 尾巴
            8019 背饰   8007 耳饰   8013 颈饰   8006 面颊
            8023 手套   8016 (名称未出现)
      100  眼睛   102  嘴巴   101  眉毛   103  脸型
3     动作   (6: 1)
9     背景
```

`field 8` 的分类预览图（角色 / 形象 / 动作 / 背景）都是 72×72 PNG，可以直接当分类图标用。

## 四、`0x9572` — 查他人的 QQ 秀

请求 body：

```
1 { 1 { 1: "9.3.75.42350" 3: 109 } 3: 2 }
2: <peer_uin>      ← 目标 uin（这个命令按 uin 寻址，不需要 uid）
```

响应 body：

```
1: ""              ← 空串（固定）
2 {                ← 该用户的形象
  1: <uin>         ← 回显 uin
  2 {              ← 穿戴部位（重复）
    1: slot        ← 部位槽位（见第七节）
    2: 商品编号    ← 如 "1015000304"
    3: "<32hex>_<5chars>_<slot>"   ← 资源定位 key（含账号级 hash，已脱敏）
    4: slot        ← 重复。**出现多个值时表示这件商品占多个部位**（连体装/套装部件）
  }
  4: "<64hex>"     ← 形象内容 hash（换装后变化，疑似校验/版本号）
  5: <unix 秒>     ← 形象更新时间
  6: 标准全身像 URL   https://images.qqshow.gtimg.com/images/v2/<uin>/<uin>_<ts>.png
  7: 动作商品编号    如 "2000000008"
  8: 高清全身像 URL   https://images.qqshow.gtimg.com/hd_images_server/<uin>/<uin>_<ts>.png
  9 { 1: 分组, 2: URL } ×2   ← 缩略图：分组 0 = images/<uin>/101.png，分组 2 = v2 版全身像
  10 { 2: 商品A, 3: 商品B }  ← 背景/特效类商品编号（如 "5000000045"/"5000000046"）
  11: <uint>       ← 常量级版本号（本次 28）
  12: "<版本>"     ← 最后一次换装的客户端版本（本次 "9.3.1"）
}
```

要点：

- `field 3` 的资源 key 里嵌着**账号级 32 位 hash**，不是商品 id 的 md5（试过几种常见
  拼接都对不上），跨账号不通用 —— 要取图直接用 `field 6/8/9` 的 URL，别自己拼。
- `field 4` 的 64 hex 是「当前形象」的内容指纹，换装即变；适合当缓存键。
- `field 7` 是**动作商品编号**（`2000xxxxxx`），`field 10` 是背景类商品编号（`5000xxxxxx`），
  这两个都是 `0x9572` 才有，`0x9b02` 里没有。

## 五、`0x9dbb_0` — 商场分类 + 商品

请求 body：

```
1 { 1 { 1: "9.3.75" 3: 109 } 3: 2 }
2: <packed varints>   ← 客户端要拉的商品分类 id 列表（顺序 = UI 顺序）
3 { 1: 2  3: 1 }      ← 未解（疑似「全部/仅套装」的分页或筛选开关）
```

`field 2` 是 protobuf 的 **packed repeated uint32**（一串裸 varint，没有 tag），本次抓包是：

```
10, 20000, 1, 5, 6, 7, 20008, 8003, 8005, 8014, 8021, 8019,
8007, 8013, 8006, 8016, 8023, 2, 100, 101, 102, 103, 3, 9
```

响应 body：

```
1 { 1 { 1: "9.3.75" 3: 109 } 3: 2 }
2 { ...分类树... } ×4          ← 与 0x9b02 同构，但多 20000 / 20008 两个聚合节点
3 {                            ← 按分类分组的商品（重复）
  1: 分类 id
  2 {
    1 { 1 { 1: "9.3.75" 3: 109 } 3: 2 }   ← 版本
    2 { ...商品... }                       ← 重复，字段见第六节
  }
  4: 1
}
```

本次样本 24 个分类组**都带 `field 2`**，但其中 10 个是空块（分类 2/9/10/101/8005/8006/
8014/8016/8021/8023 —— 本次抓包这些分类没有在售商品），只有 14 个有实际商品。
`20000 全部` / `20008 配饰全部` 是聚合节点，会把子分类的商品再列一遍 —— 解析时按分类 id
去重，别把聚合节点当成独立分类。

## 六、`0x9578_0` — 衣柜商品列表（含已拥有款式）

请求 body（较大，约 886 字节）：

```
1 { 1 { 1: "9.3.75" 3: 109 } 3: 2 }
2: 分类 id            ← 本次两次分别是 1（套装）/ 5（上装）
4 {
  1: 2  2: 1  3: 1  4: 1    ← 四个常量（未解，两次抓包一致）
  5 {
    1: <uin>                ← 自己
    2 {                     ← **已拥有槽位表**（这是「在自己衣柜里」的完整清单）
      1 { 1: slot  2: 商品编号  4: slot  5 { 1: 1  3: 0  4: 1 } }
      …
      1 { 1: slot  2: 商品编号  4: slot  5 { 3: 0 } }
    }
    3: 2                    ← 常量
    4: "<64hex>"            ← 当前形象 hash（与 0x9572 的同名字段同语义）
    5: <unix 秒>            ← 形象更新时间
    6: 标准全身像 URL
    7: 动作商品编号
    8: 高清全身像 URL
    9 { 1: 分组 2: URL } ×2 ← 缩略图
    10 { 1: 0 }             ← 常量
    11: 14                  ← 版本号（与 0x9572 的 28 不同，按命令取）
    12: "9.3.75"            ← 客户端版本
    14 { 1: 1 }             ← 常量
  }
}
5: 分类 id            ← 与 field 2 相同的值，重复一次
6: "android 9.3.75"    ← 平台串（与信封 field 6 重复）
```

**已拥有槽位表**（`field 4.5.2`）的 `field 5` 子结构有两种形态，本次 18 条里：

- `{ 3: 0 }` —— 11 条（部位 2/4/8/9/10/11/14/16/20/21/23）
- `{ 1: 1, 3: 0, 4: 1 }` —— 7 条（部位 3/7/13/15/17/18/19）

看不出与「是否穿戴」的对应关系（这两组在 `0x9572` 里都有人穿着），标为**未解**。

响应 body：

```
2 {                    ← 商品（重复，每页 30 条）
  1: "100" + 商品编号  ← 14 位完整 id（如 "1001001000401"）
  2: 商品编号          ← 10 位（如 "1001000401"）
  3: 名称（套装 / 上装 / 下装 / 鞋子 / 眼睛 …，与商场分类名一致）
  5: 预览图 URL（qqshow.gtimg.com/pcg_images/…，72×72）
  6: <unix 秒>         ← 上架/更新时间
  7: 2545603200        ← 常量（≈2050-09），疑似有效期上限
  8: 1
  9 { 1: 1  2: 1500 }  ← 尺寸：1 是比例类型标记，2 是像素边长（1500 / 300 / 600 …）
  10: <1 byte>         ← 本次恒 0x05（单字节，内容不是 varint —— 未解）
  12: 2                ← 常量
  13 {                 ← **组成部件**（重复）
    1: slot
    2: 商品编号
    4: slot
    5 { 1: 1  4: 1 }   ← 部分条目有，部分没有（未解）
  }
  14 {                 ← 标签（重复）
    1: 标签类型（1 = 通用标签，5 = 新品，7 = 节日）
    2: 文案（"新品" / "中秋"）
    3: 前景色（"#0099FF"）
    4: 背景色（"#9CA5C41A"）
    5: 展示时长？（10）
  }
  16: 1                ← 22/30 与 29/30 条出现（其余没有，疑似「可购买/上架」标记）
  19: "0.0.0"          ← 最低客户端版本
  20: "999.999.999"    ← 最高客户端版本
  25: 2                ← 常量
  31: 1                ← 只在少数单品上出现（疑似「限购/活动」标记，未解）
}
3: "start_idx=30"      ← **分页游标**：把值原样带到下一次请求即可翻页
```

关键观察：

- **套装**（分类 1）的 `field 13` 是一整套拆解：本次样本 `1001000401` 有 11 个部件
  （部位 3/7/13/14/15/16/17/18/19/21/23），正好覆盖「穿一套」需要的全部槽位。
- **单品**（如上装）的 `field 13` 只有它自己那一条。
- `field 19/20` 是客户端版本区间，`"0.0.0"`–`"999.999.999"` 表示不限制。
- 响应末尾的 `field 3` 是**分页游标**（两次抓包都返回 `"start_idx=30"`，说明每页 30 条、
  后面还有一页）。两次抓包的请求是**同一个分类的第 1 页**（`field 2` 分别是 1 与 5，
  那是分类不是游标），所以游标回填到请求哪个字段**没有抓到证据**，需要补一次翻页抓包。

## 七、编号体系：部位槽位 ↔ 商品编号段 ↔ 商场分类

这是本次逆向最主要的结论。**三套编号并存，不要混用**：

### 7.1 商品编号 = `10` + 2 位部位段 + 6 位序号

```
1001000401
│ │ └───── 序号
│ └─────── 部位段 01
└───────── 固定前缀 10
```

动作/背景类是 11 位，前缀换成 `2000` / `5000`：

```
2000000005  ← 动作（部位段 00）
5000000045  ← 背景/特效
```

完整商品 id（`0x9578` / `0x9dbb` 的 `field 1`）= `"100"` + 上面这个 10 位编号。
例：`1001000363` → `1001001000363`。

### 7.2 部位段 ↔ 商场分类（已验证）

证据是 `0x9dbb` / `0x9578` 响应里「分类 id」与「商品编号」的共现，以及 `0x9578`
请求里「部位槽位 ↔ 商品编号」的成对出现。**部位段与商场分类 id 不是同一套数字**：

| 部位段 | 商场分类 id | 名称 | 样本商品编号 |
| --- | --- | --- | --- |
| `01` | 1 | 套装 | 1001000363 |
| `03` | 8003 | 头饰 | 1003000348 |
| `07` | 8007 | 耳饰 | 1007000057 |
| `08` | 103 | 脸型 | 1008000037 |
| `09` | 102 | 嘴巴 | 1009000027 |
| `10` | 100 | 眼睛 | 1010000027 |
| `13` | 8013 | 颈饰 | 1013000115 |
| `15` | 5 | 上装 | 1015000424 |
| `17` | 6 | 下装 | 1017000295 |
| `18` | 7 | 鞋子 | 1018000410 |
| `19` | 8019 | 背饰 | 1019000075 |
| `00` | 3 | 动作（`2000` 段） | 2000000005 |

> 也就是说：**「眼睛 10、嘴巴 9、脸型 8」这类数字只在「部位段 / 商品编号」这一侧成立；
> 商场分类 id 是另一套（眼睛 100、眉毛 101、嘴巴 102、脸型 103）**，两套不能混用。
>
> 商场分类 id 自身还有两个局部规律（观测，未在更大样本上验证）：配饰子类 = `8000 + 部位段`
> （8003 / 8007 / 8013 / 8019 …），头部五官 = `100 + n`（100/101/102/103）；而
> 套装 / 上装 / 下装 / 鞋子 / 发型 这几类是另一套从 1 起的连号。**取名字一律查分类树，
> 不要按数字硬编码**。

### 7.3 只在衣柜槽位里出现、商场样本里没有的段

| 槽位 | 本次出现的商品 | 说明 |
| --- | --- | --- |
| 2 | 1002000002 | 名称未在抓包里出现 |
| 4 | 1004000236 | 同上 |
| 5 | 1005000060 | 同上 |
| 11 | 1011000031 | 同上 |
| 14 | 1014000010 | 同上 |
| 16 | 1016000001 | 同上 |
| 20 | 1020000004 | 同上 |
| 21 | 1021000002 | 同上 |
| 23 | 1023000006 | 同上 |

这些槽位在 `0x9572`（他人）与 `0x9578`（自己衣柜）里都稳定出现，商品编号段与槽位严格
相等，所以**槽位 = 商品编号第 3–4 位**这一点可以确认；只是它们的显示名没进抓包
（商场分类 2 = 发型、8 = 配饰 下面还有 8003…8023 九个，估计槽位 2/4/5/11/14/16/20/21/23
对应发型、配饰子类、手套等，需要再来一次带商品名的抓包才能坐实）。

## 八、发送「QQ 秀专有表情」

抓包里两条 `MessageSvc.PbSendMsg` 都是**私聊**（`routingHead.c2c` 只带 `uid`，没有 uin），
消息体是三个 elem：

```
elem 37  generalFlags   ← 客户端默认装扮（字体 / 挂件），不是 QQ 秀专有
elem  9  bubble { 1: 0 } ← 默认气泡
elem 53  commonElem { serviceType: 48, pbElem: <NTV2 msgInfo>, businessType: 10 }
```

### 8.1 与普通图片/动画表情的差别

```
pbElem (NTV2 上传产物 msgInfo)
1 { … files … }                  ← 与普通图片完全同构
2 {                              ← extBizInfo
  1 {                            ← pic
    1: 1                         ← bizType：普通图 0，这里 **1**
    2: "[动画表情]"              ← textSummary
    11: <bytesPbReserveC2c>      ← 见 8.2，**真正的差异全在这一块**
    1001: 1                      ← fromScene
    1002: 1                      ← toScene
  }
  10: 0                          ← busiType
}
```

| 字段 | 普通图片 | 本抓包（QQ 秀表情） |
| --- | --- | --- |
| `commonElem.serviceType` | 48 | 48（相同） |
| `commonElem.businessType` | 20 | **10** |
| `pbElem.extBizInfo.pic.bizType` | 0 | **1** |
| `pbElem.extBizInfo.pic.textSummary` | `[图片]` | `[动画表情]` |
| `pbElem.extBizInfo.pic.bytesPbReserveC2c` | `{ subType: 0 }`（2 字节） | **174 / 1934 字节**（`field 11`），见 8.2 |
| `pbElem` 其余 | NTV2 图片上传产物 | 同左（files/fileToken/rkey 一套） |

`businessType = 10` 在仓库里原本只出现在「合并转发里的图片」（`packages/protocol/src/msg/decode.ts`
的注释），这次确认**私聊直发的图片型表情也用它**。

> 仓库的 `uploadImageMsgInfo` 目前把 `bytesPbReserveC2c` 只写成 `{ subType }`（`packages/protocol/src/highway/media-upload.ts`），
> 不包含下面这些字段 —— 这是「能发出、但还原不了表情形态」的直接原因。

### 8.2 `bytesPbReserveC2c`：表情形态全在这里

两条抓包的 `extBizInfo.pic.field 11` 内容：

```
1: 1                ← subType（1 = 动画表情）
3: 0                ← 常量
4: 0                ← 常量
8: "[动画表情]"     ← 重复 textSummary
10: 0               ← 常量
12: ""  18: ""  19: ""              ← 空占位
20 { 1: 0  2: ""  3: 0  4: 0  5: 0  7: "" }   ← 空占位
30: "&rkey=<...>"                   ← 下载 rkey（与 pbElem.1 里的 rkey 同源）
31: "<大写文件名或空串>"           ← 抓包里静态那张是 32 位大写 MD5，gif 那张为空串
34: 0
```

两条的公共部分是上面这些；**gif 那条多出 `35` + `36` 两个字段**：

```
35: 3                ← 疑似「互动表情」类型标记（静态那张没有）
36 {                 ← 互动表情包定义（1785 字节）
  1:  "3000000052"                ← 主表情包 id
  2:  "2000000271" ×4             ← 一组元素 id
  3:  "<uin>"                     ← 发送者
  4:  "3000000052"
  5:  "2000000275" ×4
  6:  15
  8:  1
  9:  "#C2C2C2FF"                 ← 描边色
  10: "#E3E3E3FF"                 ← 填充色
  11: 540
  12: 540
  13: "3000000052"
  14: "2000000271" ×4
  15: "成语接龙"                   ← 玩法名
  16: 3
  17: 2
  18: 1
  19 { … } ×10                    ← 变体槽位（对应目录里的 variants）
  20 { 1: 1050  2: 1460  3: <f32> 4: <f32> 5: <f32> } ×4
  21 { …同 20 结构… } ×4
  22 { …同 20 结构… } ×4
}
```

`20/21/22` 三组 ×4 的 float 是布局参数（本次 `750.0 / 1550.0 / 1400.0`，小端字节
`00 80 3B 44` / `00 C0 C1 44` / `00 00 AF 44`）。结构与
[`resources/qqshow/show_emoji.json`](../../resources/qqshow/show_emoji.json) 里的
`preview.frames` 一致：`{1: 帧时间 ms, 2: 总时长, 3/4/5: 三个 float}`。
第二次抓包（「马力全开」）是 7 帧、`2: 1320`、float `750/3000/1200`，随玩法变化。

`field 19` 的条目形态 `{1: 主包id, 2: ×N 元素id, 3: 包id, 4: ×N 元素id, 5: 1}`
对应目录里的 `variants[i]`（`primary / secondary / mirror`），已用两份真实发送包回验命中。

### 8.3 实测：QQ 秀特殊显示的开关是 `pic.bytesPbReserveC2c` 的 `35` / `36`

**实验方法**：把抓包里的 `MessageSvc.PbSendMsg` 请求体原样重放（只改
`random` / `clientSequence` / `msgFlag` 避免重复消息抑制），再做字段级手术。

#### 结论先行

| 实验 | 内容 | 收端显示 |
| --- | --- | --- |
| 原包 2（gif） | 抓包原文，含 `35` / `36` | **正常**（有「成语接龙」互动） |
| 替换包 | 第 2 包的互动段 + 第 1 包的图片资源 | **正常**（稳定复现 2 次） |
| 原包 1（静态 jpg） | 抓包原文，**无** `35` / `36` | **回退默认表情** |
| 包 1 identity 重放 | 原包 1 逐字节相同 | **回退**（确认不是构造问题） |
| **N** | 包 2 **删掉 `35` / `36`** | **回退** ← 直接证实它是开关 |
| **O** | 包 2 **删掉 `30`(rkey)** | **正常** ← rkey 非必需 |
| **P** | 包 2 **只留 `1/30/31/35/36`** | **正常** ← 其余 8 个字段非必需 |

两个原包的 `pbElem` 已做完整结构路径对比：**唯一差异就是 `pic.11` 多了 `35` / `36`**，
其余字段（含 rkey、fileToken、内容指纹、所有显式 0 值字段）逐字节一致。

```text
35: 3                         ← 互动表情类型标记
36 {                          ← 互动表情包定义（1785 字节）
  …
  15: "成语接龙"
  …
}
```

> 这些 id 全部来自 `0x957b_0` 的表情目录（见本文第八节末「表情从哪来」及
> [`resources/qqshow/show_emoji.json`](../../resources/qqshow/show_emoji.json)）。

因此：**`35` / `36` 才是「QQ 秀专有表情」的显示开关**；只有图片本体（哪怕 rkey、
fileToken 全都对）时，客户端按普通图片渲染，也就是用户看到的「回退默认表情」。

**最小必需集合**（实测下界，见 N/O/P）：`pic.11` 里 `3/4/8/10/12/18/19/20/34`
可以全部删掉，`30`（rkey）也可删；保留 `1` + `31` + `35` + `36` 即可正常显示。
其中 `35`/`36` 是开关，`1` 是 subType，`31` 的作用待进一步确认（可能是
客户端匹配本地缓存用的名字，删掉是否仍正常尚未单独验证）。

#### 关键教训：拿「静态那张」当基准会得出错误结论

第一版实验拿**原包 1** 当对照（当时误以为它显示正常），据此得到的
「rkey / 文件名缺一不可」结论**是错的**。后续用 identity 重放（原样重发、逐字节
相同）才确认：原包 1 本身就显示失败，所有基于它的减法实验都不成立。

> 重放类实验必须先用 identity 对照确认「基准包本身是成功的」，再动字段。否则
> 减法实验的每一组「失败」都可能是基准失败造成的假象。

#### 构造流程是可靠的（已单独验证）

把原包 1 解码后立即重新编码（不做任何修改），产出的 `pbElem` 与原包**逐字节相同**
（705B，`==` 为 True）；字段顺序也保持一致（`1,3,4,8,10,12,18,19,20,30,31,34`）。
所以字段手术实验的差异只可能来自被改动的字段本身。

#### 服务端不校验这些字段

所有实验（含各种残缺形态）的回包都是 `result=0`，服务端序列号连续递增。
**回退发生在客户端渲染层** —— 「发得出去」不能作为「显示正确」的证据。

#### 重复消息抑制

同一条 `random` + `clientSequence` 重发，服务端回 `result=241`（不是 0）。
重放实验必须换 `random` / `clientSequence` / `msgFlag`，否则会误判成字段错误。

#### `35` / `36` 的内容

```text
35: 3                       ← 类型标记；两条抓到样本里只有带互动包的才有
36 {                        ← 互动表情包定义，1785 字节
  1:  "3000000052"          ← 主表情包 id
  2:  "2000000271" ×4       ← 元素 id 组
  3:  "<uin>"               ← 发送者
  4:  "3000000052"
  5:  "2000000275" ×4
  6:  15   8: 1
  9:  "#C2C2C2FF"           ← 描边色
  10: "#E3E3E3FF"           ← 填充色
  11: 540  12: 540
  13: "3000000052"
  14: "2000000271" ×4
  15: "成语接龙"             ← 玩法名
  16: 3  17: 2  18: 1
  19 { … } ×10              ← 玩法槽位，每槽 5 组 id
  20 { 1: 1050  2: 1460  3: <f32> 4: <f32> 5: <f32> } ×4
  21 { …同 20… } ×4
  22 { …同 20… } ×4
}
```

`20/21/22` 三组 ×4 的 float 是布局参数（本次样本 `750.0 / 1550.0 / 1400.0`），
结构为 `{1: 帧时间 ms, 2: 总时长, 3/4/5: 三个 float}`。对比第二次抓包（「马力全开」，
7 帧、`2: 1320`、float `750/3000/1200`）可知这些值随玩法变化，是渲染用的时间轴 + 位置。

#### 表情从哪来：`0x957b_0` 是目录接口

`OidbSvcTrpcTcp.0x957b_0` 是**互动表情目录**，一次返回全部 48 个表情包定义
（玩法包 id、元素 id、颜色、布局帧、变体列表）。发送包里的 `36` 就是
「从这个目录挑一个包 + 挑一个变体」拼出来的 —— 已用两份真实发送包回验，
`primary/secondary` 的 `packId + elementIds` 在目录 `variants` 里精确命中。

目录已离线固化为 [`resources/qqshow/show_emoji.json`](../../resources/qqshow/show_emoji.json)：
36 个「互动动作」+ 7 个「双人互动」+ 5 个「接龙」。该接口与上面四条命令同属
Android appid 白名单，PC 端调用同样返回 319，所以只能离线使用快照。

#### 对仓库的启示

`packages/protocol/src/highway/ntv2-schemas.ts` 的 `PIC_RESERVE_C2C` 只声明到
`field20`，**没有 `30` / `31` / `34` / `35` / `36`**；而
`packages/protocol/src/protobuf.ts` 的 `encode()` 只遍历 `schema.fields`，没声明的
tag 会被**静默丢弃**。所以即便把 `35` / `36` 塞进 reserve 对象也发不出去 —— 这和
`GENERAL_FLAGS` / `FONT_INFO` 那次「没声明就丢字段」是同一个坑。

要支持「QQ 秀专有表情」，需要补的是：`PIC_RESERVE_C2C` 的 schema 声明（`30`/`31`/`34`/`35`/`36`）。

互动包数据本身已有来源（`0x957b_0` 目录快照），不再是未解项。

**更大的缺口在图片侧**：QQ 秀表情的画面是客户端**本地渲染**出来的。抓到的
`v6.htdata.qq.com` HTTP 上传（`htcmd=0x6FF0087`，`PicUp.DataUp`）里，载荷去掉协议头
后是按 `fileSize` 截断的 GIF，其 md5 与 SSO 信令里的 `pbElem.1.1.1.2` **逐字节一致**
—— 即「装扮 + 动作」在本地合成成一张图再上传。因此**想在 WeQ 侧自己生成表情**，
还缺两样：各元素 id 对应的素材图、以及渲染逻辑。

## 九、实测：PC 端拿不到这些命令

用当前在线的 PC QQ（`nt_helper` 借凭据、`scripts/sso_send.ts` 发包）重放：

| 命令 | 结果 |
| --- | --- |
| `OidbSvcTrpcTcp.0x9b02_0` | `319 [oidb] rule type not match appid` |
| `OidbSvcTrpcTcp.0x9572` | 同上 |
| `OidbSvcTrpcTcp.0x9dbb_0` | 同上 |
| `OidbSvcTrpcTcp.0x9578_0` | 同上 |
| `OidbSvcTrpcTcp.0x957b_0`（表情目录） | 同上 |
| `OidbSvcTrpcTcp.0xfe1_3`（仓库已有的取 QQ 秀 URL） | **正常**，能查到 <uin> 与 <peer_uin> 的 `images/<uin>/101.png` |

排除项（都试过，仍是 319）：

- 用**抓包整帧**（含 4 字节长度前缀、含 `field 6` 平台串）直发 → 回包 0 字节；
  改用 `OidbSvc.0x9b02_0` 这个老式命令名 + 去掉长度前缀 → 回 13 字节的 319
  （`08 82b602 1000 18 bf02 22 00 2a 00`，`0xbf 0x02` = 319，只是没有错误文案）。
- 把 `setSsoSession` 的 `clientVersion` 换成 `9.3.75`（抓包里的 Android 版本）→ 319。
- 加签名（`--sign`）→ 319。
- `isUid=true` 的 UIN-form 变体 → 319。

结论：**这些命令在服务端按 appid 做了白名单分流**（与 `0x921b` 群报名、图文 Ark 的
`901501` 同源），PC/Linux 的 appid（`537391664`）不在放行名单里，换版本号/签名/信封都
绕不过去。想在 PC 侧落地只能借 Android 端的协议身份，或者放弃这四条、继续用 PC 侧可用的
`0xfe1_3` 取图。

对照：同一条通道发 `MessageSvc.PbSendMsg`（第八节那两条表情）完全正常，`0xfe1_3` 也正常
—— 所以不是注入/在线状态问题，就是命令级的 appid 规则。

## 十、待验证 / 未解

1. **元素素材与渲染**：这是自造表情的最后一道门槛。各 `2000xxx` 元素 id 对应的素材图
   不在协议里（目录只给 id），`pcg_images/*.png` 是 72×72 的包图标而非可拼接图层。
   要本地合成需要素材下载路径 + 渲染逻辑，均未解。
2. **`field 35` 的取值含义**（两次抓包均为 3），以及 `36.19` 的条目语义
   （疑似关卡/变体槽位；`20/21/22` 已确认是时间轴 + 布局 float）。
3. **槽位 2/4/5/11/14/16/20/21/23 的显示名**：缺一次「带商品名」的 `0x9572` 或
   `0x9dbb` 抓包（本次 `0x9572` 响应里那些条目只有 `field 1/2/3/4`，没有名称）。
4. **`0x9dbb` 请求的 `field 3 { 1: 2, 3: 1 }`** 与 **`0x9578` 请求的 `field 4.1..4`
   （2/1/1/1）** 的语义（疑似分页/筛选开关，两次抓包恒定）。
5. **`0x9578` 已拥有槽位表 `field 5` 的两种形态**（`{3:0}` 与 `{1:1,3:0,4:1}`）没有找到
   规律，可能是「是否在售 / 是否可租 / 是否默认」之类的标志位。
6. `0x9b02` 的 `field 4.1.3 = 2`、`0x9dbb` 的 `1: 2` 里的 `109` 这些常量的含义。

## 十一、复现方法

- 解析：抓包文件是「时间 方向 命令 seq uin size」+ hex payload，payload 前 4 字节是
  大端长度。剥掉后用 `protoc --decode_raw` 或任意 wire 解析器逐层读即可；本仓库的
  `scripts/sso_send.ts` 能直接吃掉整帧（自动剥长度前缀与 OIDB 信封），但**只能对
  PC 放行的命令用**。
- 发包：`pnpm tsx scripts/sso_send.ts --cmd <命令> --body <hex|整帧>`；需要 UIN-form 时加
  `--is-uid`，需要签名时加 `--sign`。
- 查自己的 QQ 秀图（PC 可用）：`GetQqShowUrl`（`0xFE1_3`，见
  [`packages/protocol/src/oidb/profile/get-qq-show-url.ts`](../../packages/protocol/src/oidb/profile/get-qq-show-url.ts)）。
