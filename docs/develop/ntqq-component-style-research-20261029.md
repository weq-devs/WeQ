# NTQQ 可选组件风格研究

日期：2026-10-29（北京时间）。状态：可行性研究，尚未实现 NTQQ 风格，也未完成像素级验收。

## 结论

可以把 NTQQ 的控件外观接入 WeQ 现有的「组件风格」选择器，复用业务组件、主题状态和本机持久化，不需要另写一个聊天客户端或引入 QQ 的运行时。

但「一比一」需要指定平台、版本、界面模式和外观配置：通用控件的精确复刻可以作为目标；整个窗口的精确复刻还涉及导航、栏宽、标题栏、消息排版和字体，不能只靠当前皮肤参数完成。建议以本机 QQ Mac 7.0.1（52892）的效率模式为第一份参考，不混用 Windows、Mac、旧 NTQQ 和经典模式的视觉元素。

## 实际核验

### 本机客户端

- 读取 `/Applications/QQ.app/Contents/Resources/app/package.json`：`version=7.0.1-52892`、`buildVersion=52892`、`platform=darwin`。
- 查看真实运行窗口：当前为效率模式、夜间外观；主窗口包含顶栏、左侧功能栏、会话列表、聊天区和群信息栏。
- 打开真实「通用」设置，观察模式选择、外观选择、设置分组、开关、下拉框及其展开菜单。
- 临时切到「白天」核对设置页，再恢复原有「夜间」并确认；未切换经典模式、修改聊天选项或发送消息。研究打开的设置窗口已关闭，QQ 保持运行。
- 当前字体大小滑块读数为 `3.5`。未取得设备像素比、页面缩放及控件计算样式，不能把截图像素直接当 CSS 尺寸。

### 安装包资源

标准 ASAR 目录可以枚举出 `renderer/css/pcqqkit.5360bf66.css` 等 365 个主渲染 CSS 条目；但标准 ASAR 读取的 CSS、`renderer/index.html` 均为非明文二进制，365 个 CSS 条目未能按明文 CSS 解析。未定位其封装原因，不据此宣称已取得原始 token、精确尺寸或组件源码，也不直接搬运这些文件进入 WeQ。

### 官方资料

[QQ Mac 版本历史](https://im.qq.com/macqq/support.html) 已列出 7.0.2（2026-09-24），并说明经典模式、效率模式和调色盘等能力；[QQ Linux 版本历史](https://im.qq.com/linuxqq/support.html) 也记录了两种界面模式。这说明「NTQQ 样式」并不是唯一固定画面。本轮实测对象仍是本机 7.0.1，不把官网版本记作已实测版本，也未为研究升级 QQ。

## 真实样式特征

以下为本轮可见状态的观察，不是已经测得的官方设计规格。

| 对象 | 实际观察 | 对 WeQ 的意义 |
| --- | --- | --- |
| 深浅层次 | 白天设置页为浅灰页面、白色分组、较深导航；夜间为近黑页面、深灰分组、更亮的导航区域 | 需要分别定义深浅语义 token，不能只反转颜色或给整页套透明度 |
| 强调色 | 用于功能选中、主题选择描边、开关开启和文字链接；大量普通容器保持中性 | 不应把所有边框、选中底和表面都染成主题色 |
| 设置结构 | 分组标题在容器外，容器内多行设置以细分隔线组织 | 只改按钮圆角无法获得相同观感；组件风格与页面布局应分别评估 |
| 会话选中 | 深色当前选中项是中性灰色圆角底，不是大面积蓝色底或蓝色描边 | 当前通用皮肤的主题色选中底、内描边不能直接用于 NTQQ |
| 搜索 | 主窗口搜索框为实色中性底、搜索图标和占位文字，旁边有独立加号按钮 | 应单独处理搜索框，而不是和所有输入框使用同一背景公式 |
| 开关 | 胶囊轨道、白色圆形滑块，关闭为中性灰，开启为强调色 | 需要核对轨道、滑块、内边距、开启位置和禁用态，而不只是改轨道颜色 |
| 下拉框 | 细描边、小圆角、右侧向下箭头；菜单有独立描边和阴影、条目留白、右侧勾选标记 | 应覆盖触发器与展开层两个部分，保留键盘和焦点行为 |
| 图标 | 常规工具多为单色线性图标，选中功能可切为实色强调图标 | 现有 Lucide 可支持近似效果；严格轮廓一致需要逐项比对，不能默认等价 |
| 装饰与层级 | 主界面整体平整，细分隔线分栏；设置页使用分组表面；下拉菜单有局部阴影 | 不宜使用通篇玻璃模糊或把所有圆角统一成一个值 |

本轮未核验：白天主聊天窗口的完整样本、普通消息气泡的完整对照、按钮全部状态、复选/单选框、输入错误态、右键菜单、弹窗、动画时长、经典模式、Windows/Linux 的真实运行画面。

## WeQ 当前接入条件

以下基于本轮读取的工作区，包含已有未提交改动，不代表这些能力已经发布。

| 位置 | 当前机制 | NTQQ 接入建议 |
| --- | --- | --- |
| `apps/desktop/src/renderer/src/state/theme.ts` | 六种 `componentStyles`；独立深浅、主题色、背景、密度；`data-component-style` 和 localStorage | 增加 `ntqq` 候选值，沿用状态与持久化，不另建主题 store |
| `apps/desktop/src/renderer/src/components/settings/ComponentAppearance.tsx` | 从枚举生成单选项和预览，支持方向键 | 增加真实反映 NTQQ 搜索、开关、选中行和按钮的预览 |
| `apps/desktop/src/renderer/src/styles/component-appearance.css` | 圆角、边框、表面、阴影等 skin token；通用选择器覆盖多个控件 | 保留公共机制，新增独立 `ntqq` 规则；必要时按控件拆分 token |
| `apps/desktop/src/renderer/src/im-template/styles/` | 聊天、侧栏、功能栏、编辑器、弹窗分文件 | 第二阶段分别适配，避免用一个全局选择器覆盖所有元素 |
| `apps/desktop/src/renderer/src/im-template/template/conversationLists.tsx` | 从 CSS 变量读取行高；测量 effect 依赖 `density`，并观察列表容器 resize | 若风格会改行高，加入对应重测触发；容器外框不变时不能依赖 ResizeObserver 自动发现行高变化 |
| `apps/desktop/test/browser/run-component-appearance.mjs` | 已有深浅、背景、主题色、密度、桌面/窄屏矩阵和行高检查 | 复用夹具，但更新固定行高预期与写死的选项循环断言，并新增参考图比对 |

现有 skin 规则会给非经典风格统一施加边框、圆角、弹层表面和列表内描边。只添加一组 `ntqq` 变量会继承这些行为，其中一些和实测 NTQQ 不同。应调整规则适用范围或提供明确的 NTQQ 专属覆盖，不把「能切换」当成「已复刻」。

## 建议实施顺序

### 第一阶段：NTQQ 组件风格

在现有选择器中增加「NTQQ」，默认风格不变。复用现有业务结构，先覆盖按钮、图标按钮、搜索/输入框、下拉框及菜单、开关、复选/单选、选中行、提示和弹窗。没有本轮实测样本的组件，先补参考采样再定稿。

继续尊重现有深浅、主题色、界面背景和密度选择，不暗中替用户重置。强调色仍经 `--weq-accent-effective`；NTQQ 中性表面、悬停和选中状态独立建模。不同控件分别管理圆角、尺寸、边距和状态，保留现有焦点、禁用、键盘与减少动态效果行为。

采用 QQ 对应参考色、纯色背景和参考密度时，评估接近一比一的程度；用户换色、换背景或密度后，称作同一套 NTQQ 风格的适配，不称作参考画面的像素一致。

### 第二阶段：主界面视觉对齐

如果目标包含整窗，再处理顶栏、功能栏、会话列表、聊天标题、群信息栏、消息气泡和输入工具栏。以现有布局和渲染器为基础，只有实际结构差异才增加局部呈现变体，不复制第二套消息逻辑。

WeQ 的导出、分析、助手等独有页面沿用 NTQQ 的控件语言，不虚构 QQ 中不存在的原版页面。经典模式是布局能力，不应偷偷塞进组件风格开关。

### 第三阶段：一比一验收

1. 固定参考平台、QQ 版本、效率模式、字体、字体大小、窗口内容尺寸、显示比例、深浅和主题色；记录实际值，不从截图猜 CSS 像素。
2. 采集深浅两套参考，逐控件覆盖默认、悬停、按下、焦点、选中、禁用、展开和错误状态；原版不存在的状态不强行补规格。
3. 建立相同文本和布局的合成数据组件页，使用真实 WeQ 组件，不使用真实聊天内容作为可提交测试夹具。
4. 截图叠图与像素差分结合人工查看，分别记录几何、字体、颜色、描边、阴影和图标差异；动态区域单独处理。
5. 跑既有外观矩阵，另测深滚动列表切换风格、切换密度、刷新恢复和弹层定位；行高变化不得引起空洞、重叠或点击错位。
6. 桌面端作为原版对照；窄屏 Web 验证可用性和响应式，不声称与桌面 QQ 窗口一比一。

## 本轮交付与后续决策

本轮仅新增研究文档，没有修改产品代码、设置项、版本号或 Changelog，没有运行构建和测试。源码检查与真实界面观察支持「可以接入，需按组件精细建模」的结论，不支持「已经完成一比一」的声明。

建议先做「NTQQ 组件风格」，以本机 Mac 效率模式建立第一套可复核的参考；整窗布局复刻作为后续明确选择。正式新增功能前仍按贡献流程对齐 Issue，本轮不自动创建远端 Issue 或提交 PR。
