# 未读计数：QQ 小表基准与共享快照

## 结果与来源

Desktop、Web、Remote 统一消费 `UnreadInfoService.getUnreadInfos()` 的结果。
普通私聊和群聊直接读取 QQ 的未读小表及最近会话表，不访问消息历史：

`有效阅读下限 = max(41002, 41032, 尚有效的显式 WeQ 阅读操作)`

`未读数 = max(0, 最新序号 - 有效阅读下限 - 区间内去重减计数项)`

减计数项来自 QQ 已维护的 `41024.40003`，只扣除 `下限 < seq <= 最新序号`。
`41027` 是手动未读标志，不是条数；实际数量为零时显示最小标记。
设备会话分别消费独立计数字段，不套用普通会话序号差。缺水位不把全部历史序号当成未读，
有可用计数、标志或提醒时直接展示。提醒过滤和跳转位置使用同一阅读下限，不从数量倒推。

QQ 内存读取适配器保留为显式 `compareQqCounts()` 诊断，不自动定位、轮询或接管显示。
数据库已被 WeQ 标为已读、QQ 内存仍保留角标时，WeQ 按数据库及本地操作显示，不来回切换来源。
此规则不表示 QQ 本体界面会因外部 SQL 立即更新。

## 启动与更新

账号初始化通过 `getAllUnreadInfos()` 一次读取两张小表，包含缺最近会话行的未读记录。
请求消费服务端共享快照；不同前端、不同请求批次共享初始化与刷新任务。
旧 `watermarksOnly` 参数仍可传入，但不再切换读取模式；生产结果不再使用 `countPending`。

前端首次并行获取传输批次，合并为一次状态提交，不等待聊天首屏或 QQ 内存定位，
不再逐会话精算。账号来源不变时 HMR／刷新器重建保留已显示角标和进行中的阅读保护。

服务端复用文件变化通知，50ms 合并后重读小表，比较每个会话的字段并只通知变化目标。
有订阅者时共享每 1.5 秒补查，覆盖纯阅读变化；最后一个订阅者退出后停止定时补查。
新消息通知只请求小表刷新，不另行累加消息数。读取失败或单行损坏保留已有成功快照，
后续刷新自动修正，不用零覆盖，也不转入历史扫描。

## 操作与迁移

已读写入捕获时的固定位置，并清理范围内提醒及手动未读标志；重试不追随新消息。
手动未读只置标志，不降低阅读水位。撤销恢复本次操作字段，并合并后来新增的提醒。
同会话写入串行执行，后续操作取代旧的待执行／重试操作。

`unread.json` 的新格式只保存显式阅读／标记操作，不保存 `pending` 消息集合、历史基线或观察水位。
旧格式只迁移实际本地阅读和手动操作；数据库已经超过操作位置时去掉覆盖。
保留等水位操作记录，使 QQ 后续覆写数据库时不会重新点亮已经在 WeQ 读过的旧消息。
只读目录仍只保存操作覆盖。写库失败保留本地操作并自动重试，不要求用户选择冲突。
