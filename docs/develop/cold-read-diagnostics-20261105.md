# 冷读取与数据库排队诊断（2026-11-05）

## 诊断入口

保留现有 `account.messagePerformance`，新增只读 MCP `get_message_performance`。读取快照不会执行 SQL、切换会话或修改数据；快照绑定当前已打开账号。

默认继续只采集原有有界聚合指标。受控调查时，在原启动命令前设置：

```bash
WEQ_DATABASE_DIAGNOSTICS=1 pnpm --filter @weq/desktop dev
```

本机若有专用启动脚本，应给原脚本传入这个环境变量，不另改用户配置。退出后再次普通启动即关闭逐查询采样。此改动需要主进程重新编译并重启 WeQ，无需重启 QQ；没有改版本号。

## 字段语义

`database.diagnostics` 在开关关闭时返回 `enabled: false` 和空记录；开启时包含：

- `clockOriginMs` / `sampledAtMs`：进程的单调时钟基准，可与 Unix 毫秒关联。
- `requests`：进程内生成的匿名编号、固定业务类型、开始/结束、结果、总耗时与请求内的查询总数 `queryCount`。消息窗口的串行多条查询共用编号，服务层阶段可嵌套，异步并行请求不串号。
- `queries`：匿名查询编号、请求编号、阶段、优先级、查询模板 SHA-256 的前 16 位十六进制指纹、源码函数调用点、入队/开始/结束时间、排队/原生等待、返回行数和结果。
- `runningWhenQueued`：同一调度器里该查询入队时的在途查询编号。它是观察事实，不代表整个等待都由这一条造成；还需与各查询时间区间及后续队列顺序核对。

查询历史全局最多 256 条，快照额外带最多 64 条当前在途/排队记录，避免历史轮转后丢失长期在途任务。记录只在内存；本功能不写日志或自动保存文件。不同数据库按内部路径筛选，输出不带路径。

历史可能已经轮转，且一个请求可能跨多个数据库，不能把某次快照中残留的查询之和当成请求全部耗时；先核对请求查询总数与已收集记录。`queryCount` 是调查后补充的字段，早期本轮运行采样没有该字段；报告只对完整捕获的指定请求逐条核算。

不保留 SQL、参数、正文、会话/账号标识或异常消息。调用点仅保留函数名，不保留堆栈路径。诊断开启时才生成指纹与调用点，普通运行不做这部分工作。

`nativePromiseAwaitMs` 仍包含 native 内部等待、处理和返回过程，不等于纯 SQL 执行或 CPU 时间；`nativeExecutionMs` / `nativeQueueMs` 仍为 null。排队取消不虚构原生开始时间。查询入队后的优先级提升会反映在记录中。

## 本轮实际调查

2026-11-05 使用本机正常账号与配置启动诊断实例，未修改原库、索引或未读计数算法。通过只读 MCP 读取三个已存在会话的消息页，正文仅在内存消费，保存匿名阶段数据。它是后端最新页读取验证，不是界面点击到首帧测试；MCP 路径还包含默认引用补全和多取一条的分页探测，不能与 UI 分阶段首屏混称。

真实记录中，一次私聊页服务请求总耗时约 **5444.71ms**，其中四条 SQL 累计 JS 排队 **5434.53ms**、原生等待合计 **5.53ms**。首条 `C2cMsgDb.listLatest` 入队时，同队列正在执行 `UnreadInfoDb.loadOutgoingSequences`；后者是 128 群的未读区间自己发言序号查询，原生等待约 **4773.11ms**。两个私聊均采用 sortNo 分区形式，不是该次请求自身的 UID 回退扫描造成秒级等待。

连续约 60.565 秒的采样中，观察到 447 条在此窗口完成的同消息库查询，`loadOutgoingSequences` 共 24 次，原生等待合计约 51.124 秒，占这些已完成查询原生等待总时长约 **85.52%**。累计排队可相互重叠，不与墙钟时间相加。启动阶段还捕获过一条 106 群批次原生等待约 **10.373 秒**、返回 0 行。

使用实际源码在合成明文 SQLite 中重建 SQL 指纹，确认慢指纹对应群聊批次，而非私聊 UID 回退；合成库含既有分区/序号形式的复合索引时，执行计划为分区与序号范围索引搜索加 DISTINCT 临时结构。**这不是原库的 EXPLAIN**，不能据此断言真实库全表扫描或真实索引计划。读大量未读区间后过滤自己发言、即使返回 0 行仍需检查大量消息，是与样本相符的解释，仍需实际扫描量验证。

源码放大路径：`MainView` 每 1.5 秒请求阅读水位校准；`UnreadInfoService` 在 `watermarksOnly` 且 latest > read 时标记 `countPending`，渲染层随后发起完整计数；完整计数会再进入 `loadOutgoingSequences`。当前没有针对相同水位区间的结果复用，业务上的周期校准也使用交互优先级，与首屏在同库排队。这解释了为何未点击会话仍可持续出现昂贵查询。

下一轮优化应优先围绕未读计数：避免未变化水位重复扫描、限制单批及单区间工作量、批间让出；后台优先级有帮助，但不能抢占已经执行的长 SQL。必须保留自己发送排除、读水位并发推进、手动未读、同 seq 灰条、删除/导入等反例，不通过缩小统计范围或返回旧计数来加速。

本轮只接入可复用诊断并完成定位，尚未修改上述计数算法或声称端到端问题已修复。测试实例已正常退出，采样开关未写入持久设置。
