# SIP 开启下 QQ 调试副本接入

日期：2026-11-05。实现范围：桌面签名、读取顺序、用户级副本管理与进程归属检查。
版本号不变，未发布或替换已安装 WeQ/权限助手。

## 读取契约

- WeQ 主进程的 `build/entitlements.mac.plist` 保留 electron-builder 默认运行权限，
  增加 `com.apple.security.cs.debugger`；不向渲染子进程追加调试权，也不给 WeQ 增加
  `get-task-allow`。QQ 副本保留原 entitlement，只追加后者。
- 只重签主程序，不带 `--deep`，嵌套组件保留原始签名与权限。将主程序 entitlements
  递归应用到 Helper 会丢失 `com.apple.security.inherit`，导致沙盒初始化崩溃；即便
  递归重签时保留权限，也会改变 Helper 的 Team ID，导致 Renderer 无法加载原团队
  签名的热更新 QQNT 框架。两类失败均在本机系统日志核实，与开发宿主是否签名无关。
- 管理标记记录 `signingVersion: 1`；旧标记仍识别为 WeQ 管理的副本，但需重新准备，
  不再将旧递归签名副本报告为可启动。
- `attach_elevation.ts` 在 SIP 开启时依次尝试主进程读取、现有长期助手。
  非权限错误原样返回；权限路径均不可用才给副本引导，不再提前拒绝，也不尝试无效 sudo。
- 数据库扫描已先走主进程；扫描失败后长期助手仍可尝试，SIP 判断移到临时 sudo 之前。
- 不更改账号/pid 缓存和在线能力验收规则，重启后的新 pid 沿用原有重新读取机制。

## 副本事务与 UX

`QqDebugCopyManager` 只写用户目录内固定的 `Applications/QQ-WeQ.app`，不接受 IPC 传入任意
源/目标路径。源来自已有 QQ 安装检测。使用系统 `plutil` 解析 plist、`cp -cR` 建立 APFS clone。
标记在暂存副本签名前写入 Resources，与签名一起校验。新副本签名与校验完成后才替换旧副本；
替换失败回滚，回滚自身失败保留恢复资产。事务结束清理本次暂存，不积累历史 bundle。

状态只读接口与动作分离，固定动作 prepare/verify/launch/remove；目录锁阻止多个 WeQ
实例同时操作，运行进程按可执行文件路径识别，不停原 QQ 或其他任务进程。异常退出后遗留
锁明确报路径，不自动猜测其他进程是否已完成。Web 不提供该本机管理流程。

账号选择页、账号设置、受限详情复用同一组件；持续显示检查/复制/签名/校验/启动阶段。
读取端权限、副本签名、进程存在、账号凭据是不同事实，不用启动成功冒称完整功能恢复。
启动按钮只取决于副本就绪、未运行和无在途操作，不以 `readerReady` 为前置条件。
开发 Electron 宿主可能没有 `com.apple.security.cs.debugger`，此时仍可启动副本并登录；
读取端状态继续如实显示未就绪，不将启动成功视为已获得读取权限。移除使用与其他操作一致的图标文字按钮。
参考 WCDA 的阶段式反馈与手动启动检查思路，不复用其登录期捕获或原安装替换流程：
[WCDA macOS 捕获说明](https://github.com/LifeArchiveProject/WeChatDataAnalysis/blob/main/docs/MACOS_KEY_CAPTURE.md)。

## 开发宿主准备

`pnpm dev` 现在先调用 `scripts/prepare-dev-electron.mjs --launch`，macOS 使用 APFS clone
在 `apps/desktop/dist/dev-runtime/Electron.app` 准备独立开发宿主。保留源主程序权限，
合并 `build/entitlements.mac.plist` 后仅重签主程序，通过 `ELECTRON_EXEC_PATH` 交给
electron-vite；非 macOS 继续使用依赖中的 Electron。账号目录参数保持不变。
直接执行 `node scripts/prepare-dev-electron.mjs` 只准备并输出路径，不启动 WeQ。

主程序与权限清单指纹未变且签名验证通过时复用缓存；损坏或更新时先准备、验证新宿主，
再替换旧宿主。运行中的宿主需更新时提示先正常退出，不自动停止应用。未知应用、遗留锁和
恢复资产不会被覆盖。原 `node_modules` 及嵌套 Helper/框架字节、签名保持不变。

本机 Electron 开发发行物的嵌套框架只有 linker-signed 签名、没有完整资源封印，原件的
`codesign --verify --deep --strict` 本身也不通过。因此这里只对重签后的主宿主做
`codesign --verify --strict`，不为了递归校验重签嵌套组件；另用真实 Electron 主进程、
沙盒渲染窗口启动验证可运行性。权限就绪不代替具体账号的在线能力验收。

本机桌面快捷方式对应的开发启动脚本也接入同一准备器；已打开的旧 WeQ 需要正常退出后
重新启动，QQ 副本无需退出或重新登录。准备器不修改系统设置、原 QQ 或账号数据。

本机验证：6 项 Node 针对性测试、改动文件 Biome 检查和启动脚本语法检查通过。
独立宿主实际启动 Electron 44.10.0 与隐藏沙盒渲染窗口，并对已登录 QQ 副本成功执行
原生内存扫描，确认 `a2`、`d2`、`d2Key` 存在；只记录布尔结果，不输出或保存凭据。
不带账号身份的探针未取得可选 `SecToken`，不将此次扫描表述为全部在线业务验收。
克隆宿主的 252 个框架文件及 14 个软链接与原发行物完全一致，探针已退出。
随后通过修复后的本机启动脚本完成主进程、预加载与界面构建，实际 WeQ 主进程使用
独立宿主路径；QQ 副本与其子进程也已启动。未以启动成功替代界面账号在线状态验收。

## 抓包归属

核对当前 nt_helper 实现：macOS 原生权限助手编译路径通过 PKTAP `ProcessGuard` 过滤目标
PID，原生启动返回链路类型 149 或 258；普通 `.node` 和旧助手没有这一能力。
账号自动抓包验证返回类型；旧组件启动的会话由既有 `CaptureOwnership` 异常清理路径停止，
提示修复长期授权。固定端口保留作显式诊断，不冒称全连接覆盖，也不把 14000 写成全局默认。

## 移除确认交互修复

受限详情原先固定 `z-index: 2400`，高于全局确认框动态分配的层级，真实浏览器可复现
确认按钮被详情内容拦截。详情的点外和 Escape 监听还可能在确认框处理前关闭底层详情。
现接入 `useOverlayLayer`，关闭事件仅由最上层 surface 处理，不更改实际移除接口。

回归覆盖真实 `DialogHost` 的取消、确认、Escape 与 Tab 焦点循环；启动页嵌套弹窗及
受限详情均使用合成副本状态，不删除本机副本或触碰真实 QQ。
74 项针对性单测、4 组深浅色与宽度组合的移除交互、渲染端类型检查和改动文件
Biome 检查通过；既有 36 组布局与 8 组受限面板检查继续通过。

## ASAR 移除修复

在 Electron 44.10.0 中，用合成 ASAR 归档实测 `node:fs/promises.rm` 递归删除 bundle
返回 `ENOTEMPTY`，留下归档文件，而系统 `/bin/rm -r -- <固定路径>` 可以正常移除。
副本移除、准备失败和更新后暂存清理改走现有 `runOwnedChild` 执行系统命令，锁目录
不含 ASAR，仍使用 Node 清理。删除失败时在残留 bundle 恢复已读取的管理标记，
即使 Info.plist 已被删除，也能显示需要修复并继续移除，不误判为非管理应用。

本机本次遗留目录只剩 `Contents/Resources/app/application.asar`，与原安装逐字节一致，
且无副本进程。核实后已清除该残留；未改原 QQ 安装、账号数据与热更新目录。
产品管理器复核返回 `state: missing`、无副本进程，原安装版本仍可读取。
31 项相关测试、主进程类型检查与改动文件 Biome 检查通过；独立 Electron 探针验证后
已退出并清理合成 ASAR 与一次性脚本。

## 副本权限引导

创建或更新副本成功后自动展开可跳过的权限引导，副本管理面板持续保留「权限设置」。
引导区分录屏、麦克风和摄像头：录屏可手动添加副本，音视频需先在副本中触发系统请求。
不读取 TCC 数据库、不用 WeQ 自身的权限状态代替 QQ；只报告「待确认」，由实际业务使用
确认结果。主程序的 ad-hoc 签名与原版不同，且仍保留 `com.tencent.qq`，不能沿用原版授权
或根据文件名认定系统条目会显示为 QQ-WeQ。

`qqDebugCopyPermission` 只接受固定动作枚举，打开三个系统隐私页面，或在访达中选中固定
用户级管理副本。桌面/macOS 检查复用现有入口；定位拒绝缺失、软链接和非管理副本，
不接收调用方路径或 URL。路径复制复用渲染层剪贴板 API，失败显示错误。

引导要求系统重开提示选「稍后」，从副本菜单退出后复用现有 `launch` 操作按固定路径启动；
进程存在时禁止重复启动，不强杀进程或退出原版。手动 `tccutil` 命令只在故障折叠区说明，
明确同标识原版的截图授权也会被清除，不提供自动执行入口。权限设置不阻断副本准备、
启动和内存读取。
