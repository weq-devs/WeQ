# 渲染进程恢复与诊断（2026-10-20）

## 当前范围

主窗口监听 `render-process-gone`，通过主进程的 `dialog.showMessageBox` 提供重新加载界面、退出 WeQ、稍后处理。渲染进程已经退出时，窗口关闭事件进入同一原生恢复入口，不向失效的 renderer 发送关闭确认 IPC；正常运行时仍沿用用户的关闭偏好。

恢复只由用户选择触发，不自动循环重载，不清空配置或缓存，不重放业务写请求。界面未保存的草稿可能丢失；崩溃前已经提交的操作可能仍在后台执行，用户必须先核对实际结果，再决定是否重新操作。这里没有承诺恢复未保存内容或撤销在途请求。

同一时刻最多一个提示。稍后处理后再次关闭仍可提示；页面自然加载完成、窗口销毁或应用退出后，旧提示的异步结果不能再重载旧窗口或退出应用。提示失败仅记录固定错误事件，不记录系统异常文本，下次关闭可重试。

恢复事件日志只包含固定事件、主窗口 webContents ID、白名单退出原因和退出码，不带页面 URL、账号、聊天或联系人内容。不采集堆快照，不提高堆上限，也不声称已修复内存增长根因。

- `main_window_lifecycle.test.ts`：复核单窗口复用和退出保护，合计 11 项通过；主进程 TypeScript 检查通过。
- 独立 Electron 44.9.0 离线窗口两次 `forcefullyCrashRenderer()`：实收 `reason=killed, exitCode=2`；崩溃后关闭不销毁窗口或重复提示，选择重载后恢复页面执行，第二次选择稍后再关闭后可退出。测试用可控异步选择器替代原生对话框返回，实际原生按钮尚未人工点选。

测试没有启动应用业务、读取真实 QQ 数据或重启在用 WeQ。模拟退出不是 OOM 复现，不能作为根因修复或约九小时长时验收证据。

## 有界内存诊断

主进程初始化后启动一个全局分钟采样器，退出时停止。`app.getAppMetrics()` 提供进程 PID、创建时间、类型和内存数值；按 PID 关联页面，不因多个页面共用同一进程而重复计算。用 PID 加创建时间区分进程重用，创建时间不可取得时为 `null`。不保存进程名称、账号分区、页面标题或完整 URL；只由 URL 主机名得到空间／频道类别，其余保留主界面、其他内嵌页、其他窗口类别。

主界面 preload 只响应主进程的数值采样，返回 Node/V8 堆、external、ArrayBuffer、Blink 分配与 DOM 元素数量。字段均显式标明 Bytes 或 KB；`workingSetKB` 为当前物理驻留，不等于完整私有内存，macOS 压缩也会影响解释。external 与 ArrayBuffer、进程与共享内存不可直接相加当作总占用。DOM 数量不包含不可访问的远程 frame 内部。监听器数量无法从当前无侵入接口可靠取得，固定为 `null`，不冒充零。

空间／频道及其他远程页面没有增加 preload、脚本注入、DevTools 调试连接或特权桥；只记录其进程级趋势，内部 JS 堆／DOM／监听器未知。主界面未响应时也不能推断零占用。IPC 仅接受当前主界面主 frame、请求序号、PID 都匹配且五秒内的单次回应；导航、崩溃、销毁后清除待回应状态。原始 payload 只投影有限非负数值，其他字段丢弃。

诊断文件在现有日志目录内：`memory-diagnostics.jsonl` 与 `memory-diagnostics.previous.jsonl`，每份最多 2 MiB 或 1440 条，达到任一上限轮转，只保留两份。没有内存历史数组或写入等待队列。一次快照最多 32 个进程、跟踪最多 64 个页面、每进程列出最多 8 个页面，超额数量显式记录。页面销毁即移除该页监听，退出时移除全部自建监听和定时器，不移除 Electron 或其他功能的监听。

新增验证：6 项数值／隐私／轮转回归、4 项采样周期／来源校验／迟到回应／生命周期／容量回归，连同恢复与窗口共 21 项通过。独立 Electron 44.9.0 用离线协议替身加载主页面、普通窗口以及空间／频道两个 webview，采到 7 个进程，类别关联正确；远程替身没有特权 preload。主界面实测取得堆、Blink、DOM 数值，强制 renderer 退出后能关联原 PID，停止后自建监听全部移除，输出不含夹具正文、URL 或伪 token。仅验证诊断链路，不代表真实业务内存趋势或长期稳定性已通过。

下一阶段在实际复现窗口按会话切换、历史分页、媒体、空间／频道分别观察曲线，再根据证据修复具体增长路径。约九小时运行验收独立保留，不阻塞其他产品清单项，也不从合成测试推断泄漏根因。

## 已修复的增长路径：装扮帧预热

`msgDecorationStyle.ts` 原先将每次遇到的全部帧 `Promise.all` 解码，并在全局 `liveImages` 中永久保留，没有字节、数量或并发上限。黄金夹具通过真实 `injectBubbleCss` 入口复现 50 帧同时解码，回归先失败后通过。

现在消息装扮和自身装扮使用同一个有界预解码缓存：RGBA 估算最多 64 MiB、最多 256 张，解码并发 4、等待队列 512，单次 15 秒超时。LRU 淘汰解除旧图源；失败、超大、超时和取消不保留对象，在途同 URL 去重。超过等待上限只略过可选预热，原 CSS 仍可按需取图，未修改资源协议或动画规则。64 MiB 是本缓存的估算预算，不是整个 Chromium／GPU 的内存上限。

独立 Electron 44.9.0 对照载入 `4717aa16` 的原始消息装扮模块与修复后的模块，通过本机协议生成 150 张不同的 512×512 合成 PNG；无 QQ 数据、无外部网络或模型调用。每轮 50 张：

| 指标 | 原实现 | 修复后 |
| --- | --- | --- |
| 三轮保留张数 | 50 → 100 → 150 | 50 → 64 → 64 |
| 三轮保留解码估算 | 50 → 100 → 150 MiB | 50 → 64 → 64 MiB |
| 第三轮驻留内存 | 271696 KiB | 166592 KiB |
| 同等 critical 内存压力后驻留 | 271744 KiB | 130624 KiB |

首次未施加压力的对照中，修复后驻留仍短时增长；不能把估算缓存预算冒称进程 RSS 的即时硬上限。第二次加入相同的内存压力与 GC，证实被淘汰帧可回收，原实现仍保持高驻留。两版均继续注入动画规则；完整的真实场景动画观感仍纳入后续验收。

14 项预热／缓存／装扮导出／报告字体针对性回归及渲染类型检查通过。合成对照证明的是这一条资源保留路径，不足以断言它是历史三次 Blink OOM 的唯一来源。
