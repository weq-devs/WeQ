# profile_info.db — 资料数据库

`profile_info.db` 存**人**：好友、陌生人、机器人、公众号的资料，以及好友列表和分组。
本栏目的内容全部由 WeQ 依据自己的解析实现手写维护。

对应 WeQ 解析实现：

| 文件 | 职责 |
| ---- | ---- |
| `packages/db/src/profile/profile_info.ts` | 取行 + 列 → `UserProfile` |
| `packages/codec/src/proto/profile/21000.ts` | `21000` 扩展资料列的 protobuf |
| `packages/codec/src/proto/profile/20057.ts` | `20057` 自定义状态列 |
| `packages/codec/src/proto/profile/20072.ts` | `20072` 密友关系列 |

## profile_info_v6 — 资料主表

44 列，是这个库的绝对主体，单独成篇：**[profile_info_v6 详解](./profile-info-v6.md)**。

一句话概括它的定位：**这是一张缓存表，不是好友表**。5 万多行里只有 195 个是好友，
其余全是「在群里见过一面」的陌生人。判定谁是好友要去 `buddy_list`，不能靠这张表有没有行。

## buddy_list — 好友名单

四列，短小但**权威** —— 判定「是不是我好友」以这张表为准。

| 列 | 含义 | 置信度 |
| -- | ---- | ------ |
| 1000 | uid（主键） | 已验证 |
| 1001 | QID（个性 ID，多数为空串） | 已验证 |
| 1002 | uin（QQ 号） | 已验证 |
| 25007 | 所属分组 id，对应 `category_list_v2` 的分组。**未分组的好友这里是 NULL 而非 0** | 已验证 |

它与 `profile_info_v6` 同库，所以「好友 + 资料」是一次普通 JOIN，不用跨库：

```sql
SELECT b."1000", b."1002", p."20002", p."20009", p."20070"
FROM buddy_list b
LEFT JOIN profile_info_v6 p ON b."1000" = p."1000"
ORDER BY COALESCE(p."20070", 0) DESC   -- 按亲密度排
```

这正是 WeQ「好友亲密度排行」用的查询（`listFriendsByIntimacy`）。用 `LEFT JOIN` 而非
`INNER JOIN` 是因为**存在有好友关系但资料行缺失的情况**，用内连接会悄悄少人。

## category_list_v2 — 好友分组

只有 1 行，因为**所有分组打包在一个 BLOB 里**（`25011`），不是一组一行。

| 列 | 含义 | 置信度 |
| -- | ---- | ------ |
| 1000 | 自己的 uid | 已验证 |
| 25006 | 好友总数（实测 1640，含单向/历史） | 推测 |
| 25013 | 另一个计数（实测 644） | 推测 |
| 25012 / 20075 | 两个毫秒时间戳（版本 / 拉取时间） | 推测 |
| 25011 | **分组定义列表**，protobuf | 已验证 |
| 25015 | 序列号 | 推测 |

`25011` 的结构 —— 外层 tag 与列号同为 `25011`，repeated，一项一个分组：

```text
25011 (BLOB)
└── 25011  分组项 (repeated)
    ├── 25007  分组 id
    ├── 25008  分组名
    ├── 25009  排序序号（本机恒等于分组 id）
    └── 25010  组内好友数
```

本机实测（5 个分组）：

| 25007 分组 id | 25008 分组名 | 25010 人数 |
| ------------- | ------------ | ---------- |
| 0 | 我的好友 | 185 |
| 1 | 日本朋友 | 1 |
| 2 | 家人 | 3 |
| 3 | 同学 | 4 |
| 4 | 老师 | 2 |

> ⚠️ **`buddy_list."25007"` 在本机 185 行是 NULL**，只有被手动分过组的 10 个好友有值。
> 也就是说「默认组」是靠 **NULL** 表达的，不是靠写 `0`。按 `25007 = 0` 查默认组会查空 ——
> 要用 `COALESCE("25007", 0)`。这是本页最容易踩的一个坑。

## profile_info_adelie — AI 机器人

**88 列**，是全库列数最多的表，但只装 QQ 官方 AI 机器人（本机 4 行：元宝小 Q、Q 群管家等）。
`adelie` 是 QQ 内部对这套 AI 体系的代号（会话类型 `KCHATTYPEADELIE = 42` 也是它）。

| 320047 | 创建/更新时间（unix 秒） | 观测一致 |

## 其余小表

**`profile_info_public_account`** —— 公众号/服务号，6 列：`1000` uid、`1002` uin、
`20002` 名称（本机全空）、`410001` 类型码（实测恒为 3）、`410002` 更新时间（毫秒）、`20032`。

**`user_sec_quality_table`** —— 只有自己一行，`20501` 是个 6 字节 protobuf，解出来只有
`{ 20501: { 1: 1 } }` 一个位。样本只有 1 个，语义不下结论。

**`user_tab_table`** —— 只有自己一行，`49572` 是资料卡页签配置，repeated：
`[{49573:2, 49574:1}, {49573:1, 49574:0}]` —— 两个页签项，各带一个 id 和一个显隐/顺序位。

## FTS 表打不开是正常的

`profile_info_v6_fts` / `profile_info_public_account_fts` 用 `PRAGMA table_info` 一碰就报：

```text
Error: no such tokenizer: pinyin_letter
```

这不是解密失败，而是这两张虚拟表声明了腾讯自己实现的**拼音分词器**，SQLite 本体没有它。
所以：

- **别去查 `*_fts` 虚拟表**，会直接抛错；扫全库表清单时要 try/catch 包住。
- 想要索引内容，读它的影子表 `*_fts_data` / `*_fts_idx` / `*_fts_docsize`（普通表，能读）。
- 按昵称搜人不要指望 FTS，直接 `LIKE` 扫 `profile_info_v6."20002"` 就行 —— 5 万行 SQLite 扛得住。
