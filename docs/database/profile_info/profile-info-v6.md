# profile_info_v6 — 资料主表

`profile_info.db` 的绝对主体：44 列，一行 = 一个人的完整资料。
好友、群友、只在某个群里发过一句话的陌生人，全在这一张表里。

对应 WeQ 解析实现：

| 文件 | 职责 |
| ---- | ---- |
| `packages/db/src/profile/profile_info.ts` | 取行 + 列 → `UserProfile` |
| `packages/codec/src/proto/profile/21000.ts` | `21000` 扩展资料列 |
| `packages/codec/src/proto/profile/20057.ts` | `20057` 自定义状态列 |
| `packages/codec/src/proto/profile/20072.ts` | `20072` 密友关系列 |

---

## 一、这张表的定位

**它是缓存，不是名册。** 本机实测 52243 行，其中好友只有 195 个 —— 99.6% 是陌生人。
只要你在群里见过某人一次，QQ 就会把他的昵称/头像塞进这张表，方便下次渲染群消息时不用回源。

由此推出三条写代码时的铁律：

1. **判定「是不是好友」必须查 `buddy_list`**，不能靠这张表有没有行。
2. **陌生人行是残缺的**。5 万行里只有约 4.8% 填了生日/性别/年龄这批「资料卡字段」，
   剩下的只有 uid / uin / 昵称 / 头像四样。所以任何字段都要当可空处理。
3. **行可以比现实旧**。资料是拉过一次就留着，对方后来改了昵称，这里不会自动跟。

另一个反直觉的点：**头像 URL（`20004`）只有 19.9% 的行有**。剩下 80% 连头像都没缓存。
这就是 WeQ 走 `md5(md5(md5(uid)+uid)+uid)` 本地头像路径推导、而不是依赖这一列的原因。

## 三、`21000` — 扩展资料（最大的一列）

整张表最复杂的东西。BLOB，本机 6% 的行有，中位数 195 字节，**最大 9784 字节**。
外层 tag 与列号同为 `21000`，里面按 `2200x` 分成七个功能块：

```text
21000 (BLOB)
└── 21000
    ├── 22003  好友互动标识（拍一拍/一起看/情侣…）
    ├── 22004  VIP 与特权
    ├── 22005  扩展资料（星座/生肖/地区/教育/兴趣/老资料）
    ├── 22006  隐私与状态开关

    └── 22009  QQ 空间相册
```

本机全量扫描（682 个非空行）共观测到 **142 条 tag 路径**。下面只记已定性的。

- **不是昵称颜色 RGB** —— 与超级会员开通状态无相关性（开通超会的 16 有色/36 全零，

  四川、广东、北京、英格兰、台湾、福建）。

数值集中在 48~57 和 97~108 这两段，恰好是 ASCII 的 `'0'~'9'` 和 `'a'~'l'`，
更像是某个字符串被逐字节拆开存的。**留作未解。**

## 四、`20017` — 头像摘要

小 BLOB（44~56 字节），19.6% 的行有。结构很简单：

```text
20017 (BLOB)
└── 20017
    ├── 20100  头像 md5（32 位 hex）—— 与 20101 二选一
    ├── 20101  头像 md5（32 位 hex）—— 与 20100 二选一
    ├── 20102  头像更新时间（unix 秒）
    └── 20103  同上，或 1
```

实测 783 行里 `20100` 出现 637 次、`20101` 出现 146 次，**从不同时出现**。
两者应该是「默认头像 / 自定义头像」之类的区分，但没有证据，暂不下结论。

已经**排除**的两个猜想（各 60 样本，0 命中）：

- 它**不是**本地头像文件名 hash `md5(md5(md5(uid)+uid)+uid)`（见 [头像 hash 公式](../../principles/avatar-hash.md)）。
- 它**不出现在** `20004` 那个 CDN URL 的 `ek=` 参数里。

确定成立的一条：**`20102` 与列 `20016` 恒等（60/60）**，所以这两个是同一个时间戳的两份拷贝。

## 七、`24105` — 签名富文本

**不是 protobuf**，是 QQ 老式的 `[u8 tag][u8 len][payload]` TLV 串。
本机 436 行**全部**能被这个格式完整解析（436/436），且其中 417 行的内容里含 `20011` 的纯文本签名 ——
所以它是签名的**富文本版本**，`20011` 是它的降级纯文本副本。

| tag | 含义 | 置信度 |
| --- | ---- | ------ |
| `0x03` (3) | **签名正文**（UTF-8）。436 行全有 | 已验证 |
| `0x04` (4) | **地理位置文本**（「电子科技大学(清水河校区)」「荷兰阿姆斯特丹」「网安学院图书馆」） | 已验证 |

| `0x90` (144) | 元数据串：**开头就是这个人的 uin**，后接 28 位十六进制（如 `1707889225` + `69fcb339…`） | 观测一致 |
| `0x91` / `0x92` (145/146) | 4 字节大端整数，绝大多数为 0 或 1 | 推测 |
| `0x81` / `0x82` (129/130) | 8 字节，几乎全 0 | 推测 |
| `0x95` (149) | 零长度占位（58 次） | 推测 |
| `0x01` (1) | 出现 1 次，内容「祈愿平安」 | 推测 |

解析注意：`len` 是**单字节**，所以单段最长 255 字节。签名超过这个长度会怎么切分没有样本，
本机最长的一行 324 字节也是靠多段拼出来的。

## 九、没找到的东西

诚实记录两个**确认不在这个库里**的字段，省得下次再翻一遍。

### QQ 等级

全库找过，**没有**。筛查方法：QQ 等级的形态特征是「好友几乎人人有、取值 1~256 连续宽分布」，
按这个形态扫了 195 个好友行的全部 44 个标量列 + `21000` 里的全部整数 tag，
形态匹配的候选只有这些，逐个排除：

| 候选 | 为什么不是 |
| ---- | ---------- |
| 列 `20007` / `20008` | 是出生月（1~12）和出生日（1~31） |
| 列 `24103` | 是年龄，与生年吻合 179/180 |
| `21000.22004.20448` | 是 SVIP 等级（1~9），只有开通的人有 |
| `21000.22004.28004` | 同上，与 20448 命中 22/24 |
| `21000.22004.28027` | 上限只到 26，且只有 66/195 好友非零 |
| `21000.22005.20018/20019` | 星座 / 生肖，都是 1~12 |

**结论：QQ 等级是现拉的，不落库。** 合理 —— 等级每天变（活跃度累加），
缓存进本地库只会立刻过时，客户端显示时走接口反而更简单。

### 昵称颜色 / VIP 颜色

同样**没有**。唯一形似的 `21000.22005.20021`（`"49-102-55"` 三段串）已在
[22005 节](#22005--扩展资料) 排除 —— 与超会状态无关，与地区也无关。

**推论：昵称颜色是客户端按 `bizId` + `level` 算出来的，不是存下来的。**
`21000.22004.20059` 里已经有完整的特权清单（谁开了超会、几级、图标 URL 是 `big_light_4` 还是 `gray_0`），
客户端拿这些就够渲染颜色了，没必要再存一份颜色值。

## 十、常见查询

WeQ 实际读的列（`profile_info.ts` 的 `SELECT_COLUMNS`）：

```sql
SELECT "1000","1001","1002","20002","20004","20006","20007","20008",
       "20009","20011","20014","20057","20070","20072","24103","24104","21000"
FROM profile_info_v6
WHERE "1000" = ?
```

按昵称搜人 —— **不要用 FTS**（`pinyin_letter` 分词器不存在，见 [库总览](./index.md#fts-表打不开是正常的)）：

```sql
SELECT "1000","20002" FROM profile_info_v6 WHERE "20002" LIKE ? LIMIT 50
```

批量补昵称（WeQ 的 `nicksByUids`，避免 N 次单查）：

```sql
SELECT "1000","20002" FROM profile_info_v6 WHERE "1000" IN (?,?,?,…)
```
