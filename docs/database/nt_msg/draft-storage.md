# draft_storage_table_v1 — 草稿

`nt_msg.db` 里的**草稿表**，一行 = 一个会话里「输入了但还没点发送」的内容。

> WeQ **读写**这张表（2026-09-25 起）：草稿不再由 WeQ 自己缓存，直接落 QQ 的这张表，
> 与 QQ 客户端共用同一份状态。对应实现见文末「对应实现」。
> 内容来自手工逆向：解码真实行 + 拿里面的会话标识回查联系人 / 群资料对缝。
> 样本量很小（累计观测 3 行），未观测到的部分一律留白。

解析时可用同构邻表 [hidden_session_storage_table_v1](./hidden-session.md) 的
[`43002.ts`](../../../packages/codec/src/proto/msg/43002.ts) 当解码外壳的参照
（两表外壳都是「外层 tag = 列号，内层一个子消息」）。

---

## 一、这张表的定位

关键认识：**草稿是「半条消息」，不是「一条消息」。**

用户在输入框里打字、还没按发送，QQ 就把这半成品落到这里；按下发送后这一行被移除
（或下次输入时被新内容原地覆盖）。由此推出三条性质：

- 它是**端侧本地状态**，不参与消息同步 —— 换台设备登录看不到别的设备上的草稿；
- 它与 `c2c_msg_table` / `group_msg_table` 完全独立 —— 草稿在这里，消息在那里；
- 它会**间接影响会话列表的排序**：`recent_contact_v3_table` 上有一列草稿时间（`41108`），
  以及由它参与的排序键 `41136` —— 输入框里打了字，那条会话会被顶到列表前面。
  见 [recent-contact · 草稿与置顶标记](./recent-contact.md#草稿与置顶标记41103--41104--41108)。

## 二、列结构

整张表只有 2 列（不是节选）：

| 列 | 字段名 | 类型 | 含义 | 置信度 |
| -- | ------ | ---- | ---- | ------ |
| 43001 | `storageKey` | TEXT | 行主键。格式 `0_{chatType}_{会话标识}`，见第四节 | 观测一致 |
| 43002 | `entry` | BLOB | protobuf 载荷，见第三节 | 已验证 |

建表语句与同库的 `hidden_session_storage_table_v1` 完全同构：

```sql
CREATE TABLE draft_storage_table_v1([43001] TEXT PRIMARY KEY,[43002] BLOB)
```

自带的 `draft_storage_table_v1_idx43001` 与主键 autoindex 重复（同列、同序），
属冗余索引，读取路径用不到。

这张表**没有独立的会话标识列、没有预览列** —— 会话身份要从 `43002` 里解（或从 `43001` 拆），
草稿正文也只有解 `43002` 才看得到。

> 上面是 `PRAGMA table_info` 的全量结果，不是节选 —— 这张表实打实只有 2 列。

## 三、`43002` — protobuf 载荷

外壳里只有一个 tag 同为 `43002` 的子消息，内含一条「草稿消息」：

```text
43002 (BLOB)
└── 43002  DraftEntry
    ├── 40001  msgId      ← 草稿恒为 0（没发送，还没有真实 msgId）
    ├── 40010  chatType   ← 会话类型，枚举同 recent_contact · ChatType
    ├── 40021  targetUid  ← 会话标识：c2c 是对端 uid，群是群号
    ├── 40022  —          ← 观测到恒为空串，含义未定
    ├── 40050  sendTime   ← 草稿的写入时间，unix 秒
    ├── 40800  msgBody    ← 草稿正文，一条消息段（element）
    └── 49079  —          ← 观测到恒为 0，含义未定
```

tag 取值直接沿用消息行与 `recent_contact_v3_table` 的同一套约定
（`40010` 会话类型、`40021` 会话标识、`40050` 时间、`40800` 正文），
等于把半条消息按消息行的编码方式存了进来。所以 `40010`/`40021` 的语义、`40010` 的取值表
可以直接翻 [recent_contact · ChatType](./recent-contact.md#四chattype会话类型)，
正文的解析翻 [消息行](./row.md) / [40800 解析](./40800.md)，此处都不重复。

两个观测恒定的 tag 不猜含义：`40022` 与 `recent_contact_v3_table` 的同名列一样是空串，
`49079` 恒为 0。在拿到反例之前按「原样保留」处理。

### 正文（40800）

**`40800` 在这里直接就是一条 element**（`repeated`），与消息行的
`{40800: {40800: ElementWire}}` **差一层** —— 消息行外层那个 40800 里面才是
`MsgBody`，草稿里外层就是 element 本体，`elementType` 在 `45002` 判别、各类型
字段平铺同一层（详见 [40800 解析](./40800.md)）。

这一点是 2026-09-25 用三条真实草稿实测出来的；早期只观测到单段纯文本，容易误以为
它和消息行完全同构。**一条草稿可以带多个元素**，实测到的组合：

| 会话 | 40800 数量 | 元素 |
| ---- | ---------- | ---- |
| `0_1__…LKt3…` | 2 | TEXT「表情缓存」+ FACE(`faceId=178` 斜眼笑) |
| `0_2__673646675` | 2 | TEXT「群聊的图片缓存」+ PIC(本机 `nt_data/Pic/…/Ori/*.png`) |
| `0_1__…h3h1…` | 1 | TEXT「文字换成」 |

所以**解析必须按 40800 全量走**：@ / 图片 / 视频 / 文件 / markdown / ark / 引用……
所有 element 类型都可能出现，不能只支持样本里见过的那几种。

单段纯文本的样本长这样：

```text
40800 (BLOB)
└── 40800  ElementWire
    ├── 45002  elementType = 1        （TEXT）
    └── 45101  textContent = "mmm"
```

与消息行对比，同一段文本的编码有两处可见差异：

| | 真实消息行 | 草稿 |
| -- | ---------- | ---- |
| `45001` elementId | 有（雪花 id） | **没有**（草稿还没发送，elementId = 0 被省略） |
| `45102` 之后 | 直接收尾（只剩 `45102 = 0`） | `45102`~`45111` **逐个显式写零**（`45105`/`45110` 写空串） |

也就是说**草稿的编码比消息行更啰嗦**、且不带 elementId，但两边的解码结果一致，
解析器不必区别对待 —— 唯一要留意的是别拿 elementId 有没有去判「是不是草稿」，
那属于实现细节。

样本都是纯文本，图片 / 引用 / @ 等其它 element 类型在草稿里长什么样没有观测，
不排除有差异 —— 读的时候保持 [40800 容错解码](./40800.md#六容错解码sanitizebytes) 的心态。

## 四、`43001` — 行键的解析

行键把会话身份拼进字符串里，与载荷里的 `40010` + `40021` 一一对应：

```text
0_{chatType}_{会话标识}
│    │           └─ c2c：对端 uid；群：群号
│    └─ 40010 会话类型（数字）
└─ 固定前缀 "0"，含义未定
```

实测三行：

| 43001 | 拆解 | 对应会话 |
| ----- | ---- | -------- |
| `0_1__u_LKt3AdAIMP-CUfn6ydzDzw` | prefix `0` / chatType `1` / uid `u_LKt3AdAIMP-…` | 好友 eSTKim（uin 2863253201） |
| `0_2__673646675` | prefix `0` / chatType `2` / 群号 `673646675` | 群「喵喵喵」 |
| `0_2__1090396070` | prefix `0` / chatType `2` / 群号 `1090396070` | 群「开心快乐的跑步」 |

需要说明的是，与本表同构的 [hidden_session_storage_table_v1](./hidden-session.md#二列结构)
把它的 `43001` 记成**不透明 key**、明确「不要解析它猜含义」。这里之所以敢拆，是因为
每行样本都能稳定拆出合理的 chatType + 会话标识、且与载荷内容完全吻合。因此本列记为
**有规律**（置信度「观测一致」而非「已验证」），解析路径仍**优先用载荷里的 `40010`/`40021`**，
`43001` 只当交叉校验，别反过来依赖它。

还要注意 chatType 前后的**双下划线**：`0_1__u_…` 实际是「`0` + `1` + 空串 + `u_…`」拼出来的，
并不是 `split('_')` 那种均匀结构。真要拆，按**第一个**和**第二个** `_` 切两刀，
第三段整体当会话标识（uid 自带下划线，不能继续切）。

## 五、与会话列表的关联

草稿本身只落在这张表里，但会话列表需要知道「哪个会话有草稿、多新」，于是
`recent_contact_v3_table` 上留了一份**时间镜像**：

| 列 | 与草稿的关系 | 置信度 |
| -- | ------------ | ------ |
| `41108` | = 本表同会话行的 `40050`（草稿更新时间），无草稿时为 0 | 已验证 |
| `41136` | 排序键 `2^47 × [已置顶] + 有草稿 ? 草稿时间 : 40050` | 观测一致 |

三个会话的对照样本（含一个**未置顶**的草稿群，用来排除置顶干扰）：

```text
会话                    本表 40050    contact.41108   contact.41136
673646675       (置顶)   1790184773    1790184773      2^47 + 1790184773
u_LKt3…         (置顶)   1790184913    1790184913      2^47 + 1790184913
1090396070      (未置顶) 1790185263    1790185263      1790185263
```

也就是说 `41108` 是**跨表冗余**：QQ 从会话列表就能判断草稿状态，不必 join 本表。
详尽的推导与排除过程见 [recent-contact · 草稿与置顶标记](./recent-contact.md#草稿与置顶标记41103--41104--41108)。

> 注意 `41108` **不是 trigger 写出来的** —— `nt_msg.db` 里一条 trigger 都没有
> （`sqlite_master` 里 `type='trigger'` 零行）。它由 QQ 进程在草稿变动时自己写。

### 直接写表会被 QQ 认吗？

实测（2026-09-24）。用 SQL 往本表插一条私聊草稿（`40050` 故意写成两小时后的未来时间
`1790190735`），观察到：

- **QQ 界面毫无反应** —— 输入框、会话列表都没变化，也没见到任何即时读表行为；
- 随后在 QQ 里真的改动了这个会话的草稿，**这一行被整体重写**：`40050` 从我们写的未来值
  变成真实编辑时间，正文也换成了用户实际输入的内容，`recent_contact_v3_table.41108`
  同步等于这个新时间（期间还看到 7 秒内连写两次：`1790184906` → `1790184913`）。

后半段是硬结论：**QQ 保存草稿是整行覆盖**，它只认自己进程内的状态，落盘时按自己的版本
重写整行，外部写进去的 `40050` 不会被当成「已有草稿」留下来。

至于「SQL 写入会不会触发 `41108`」——**没验证**。插入后我们只回读了本表（确认未来值写进去了），
没有在同一时刻取 `41108` 的样本；等再看时，那一行已经被 QQ 重写过了。
所以「QQ 不监听这两张表」目前只有「界面无反应」这一条间接证据，别当成已验证。

反方向（QQ 会不会把库里已有的草稿读回输入框）**同样没结论**：这次观测到的正文与插入值相近，
但当时用户在输入框里有编辑动作，分不清是「QQ 读回来的」还是「用户自己敲的」。
要验证得关掉 QQ、纯 SQL 造一行、再启动 QQ 看输入框 —— 还没做。

> 要用 SQL 造草稿做实验，记住 QQ 随时可能用内存状态把那一行盖掉；**先关 QQ 再写**。

## 六、常见查询

整表读（实测只有几行，无需分页）：

```sql
SELECT "43001","43002" FROM draft_storage_table_v1;
```

按会话取单条草稿（c2c 填 uid、群填群号）：

```sql
SELECT "43002" FROM draft_storage_table_v1 WHERE "43001" = '0_1__<uid>';
```

`43002` 解码同样先过 `sanitizeBytes` 容错（原因见
[40800 · 容错解码](./40800.md#六容错解码sanitizebytes)），
一行烂掉的草稿不该拖垮整个读取路径。

## 七、对应实现

| 层 | 位置 | 干什么 |
| -- | ---- | ------ |
| codec | `packages/codec/src/proto/msg/43002_draft.ts` | `43002` 载荷的 protobuf 形状（40800 按 `repeated ElementWire` 声明） |
| db | `packages/db/src/contact/draft.ts` | `DraftDb`：整表读 / 单会话读 / 整行写 / 删；元素逐个走 `decodeElement` |
| db | `packages/db/src/contact/recent_contact.ts` | `RecentContactDb.setDraftTime`：同步会话列表镜像 `41108` / `41136` |
| service | `packages/service/src/account/draft.ts` | `DraftService`：把「写草稿」组合成「写本表 + 同步 recent_contact」 |
| IPC | `apps/desktop/src/main/ipc/routers/account.ts` | `account.listDrafts` / `account.saveDraft` |
| 渲染层 | `apps/desktop/src/renderer/src/im-template/template/draftElements.ts` | 元素数组 ↔ 输入框文本（输入框表达不了的元素编成元素 token 无损往返） |

写入时机（产品决定，刻意不做逐字写、也不做本地兜底）：

- **离开会话**（切到另一个会话）时，把上一个会话的脏草稿写回；
- **离开消息页**时，把当前所有脏草稿写回；
- **应用退出 / 窗口关闭**（`beforeunload`）时尽力再写一次。

WeQ 意外退出导致没写成，就按**没有草稿**处理 —— 不往本地缓存回落。写库失败（QQ
离线、库被锁）同样直接失败并丢这次草稿。
