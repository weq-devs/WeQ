# 40801：消息装扮信息

`40801` 是 `c2c_msg_table`、`group_msg_table` 和 `dataline_msg_table` 中的消息装扮列，保存每条消息对应的气泡、聊天字体和挂件等信息。

截至 **2026 年 8 月 23 日**，WeQ 已完成该列的主要字段解析。该列本质上是一个 protobuf：外层使用 tag `40801` 包裹，真正的装扮字段位于内层消息中。

对应实现：

| 文件 | 职责 |
| ---- | ---- |
| `packages/codec/src/proto/msg/40801.ts` | `40801` 的 wire schema |
| `packages/codec/src/domain/msg/msg_dress.ts` | 解码并提取气泡、字体、挂件 ID |
| `packages/service/src/account/msg_decoration.ts` | 根据 ID 解析装扮资源 |

---

## 一、整体结构

```text
40801 (BLOB)
└── tag 40801 (LEN / nested)
    ├── tag 41510  bubbleId
    ├── tag 41525  fontId（优先）
    ├── tag 41528  widgetId
    └── tag 41531  fallback font value（备用字体 ID）
```

外层 `40801` 是列本身的 protobuf 字段，内层字段不能直接按列号解释。

## 二、已确认的装扮字段

| 内层 tag | 字段名 | 类型 | 含义 | 备注 |
| ---: | ---- | ---- | ---- | ---- |
| `41510` | `bubbleId` | `uint32` | 气泡皮肤 itemId | 直接使用 |
| `41525` | `fontId` | `uint32` | 聊天字体皮肤 itemId | 字体 ID 的首选来源 |
| `41528` | `widgetId` | `uint32` | 挂件 itemId | 直接使用 |
| `41531` | `flag41531` | `uint32` | 备用字体值 | 需要按规则解码后才能得到字体 ID |

## 三、字体 ID 获取规则

字体 ID 的读取顺序如下：

1. 如果 `41525` 存在且不为 `0`，直接将 `41525` 作为字体 ID。
2. 如果 `41525` 为 `null` 或 `0`，读取 `41531`，记为 `stored`。
3. 使用下面的公式解码：

```text
fontId = ((stored & 0xFF) << 8) | ((stored >> 8) & 0xFF)
```

4. 解码结果为 `0` 或没有结果时，视为未设置聊天字体。

例如：

```text
stored = 0x1234
fontId = 0x3412
```

这里的 `41531` 不是直接可用的字体 itemId，而是一个低 16 位字节序交换后的值。

### 注意：`41531` 还有 bit 16 标志位，解码时会被掩掉

真机 `41531` 不只低 16 位：**bit 16 是一个标志位**。实测（`c2c` / `group` 各数百行）：

- 真实字体 54981（=`0xD6C5`）对应的 `41531 = 116182 = 0x1C5D6` —— 比 `swap16(54981) = 0xC5D6`
  多一个 `0x10000`；
- 没有字体的消息 `41531 = 65536 = 0x10000`（低 16 位为 0，只留标志位）；
- `41525`（首选字体）实际很少非零，字体基本都走 `41531` 这条回退路径。

上面的解码公式用 `(stored >>> 8) & 0xFF` 把 bit 16 掩掉 —— 这对「读出 itemId 给人看 / 查资源」
是对的，但**不要把解码出的 itemId 再编码回 wire**（那会丢失标志位）。

### 与消息元素（PushMsgBody）的恒等映射

`40800`（消息正文）里**不存**逐条装扮 —— 装扮只在 `40801` 列。发送 / 推送时的元素级装扮与
本列字段是**恒等**的（真机 `41531 = 116182` 与元素 `generalFlags.font.fontId2 = 116182` 相等）：

| 40801 | 消息元素 |
| --- | --- |
| `41510` | tag 9 `bubble.id` |
| `41525` | tag 37 `font.fontId1`(56) |
| `41531` | tag 37 `font.fontId2`(15) |
| `41528` | tag 37 `widgetId`(17) |

所以转发已有消息时应当**原样透传**这四个原始值（codec 的 `MsgDecoration.fontId1Raw` /
`fontId2Raw` 保留的就是它们），绝不能「解码 → 自己编码」——那会丢 bit 16、也会把字体写错槽位。

## 五、解码后的使用链路

`decodeMsgDressColumn` 输出统一结构：

```ts
{
  bubbleId: number;
  fontId: number;
  widgetId: number;
}
```

后续资源解析和渲染只使用这个统一结构：

- `bubbleId` 用于解析气泡资源；
- `fontId` 用于获取和注入聊天字体资源；
- `widgetId` 用于解析挂件资源。

当三个 ID 都为 `0` 时，解码结果为 `null`，表示该消息没有可用的装扮信息。
