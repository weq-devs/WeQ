# msg_unread_info_table — 未读信息

`nt_msg.db` 里记录每个会话**读到哪了**的表，两列而已，但第二列是一个嵌套 protobuf，
里面藏着「特别关心 / @我 / @全体 / 回复我 / 新文件 / 群公告 / 群提醒词」这些提醒标记 —— 它们**不是**独立的列或表。

对应 WeQ 解析实现：

| 文件 | 职责 |
| ---- | ---- |
| `packages/db/src/msg/unread_info.ts` | 取行 + 展平高亮 → `UnreadInfoResult`；`markRead()` 抬已读 seq、清高亮组 |
| `packages/codec/src/proto/msg/48902.ts` | `48902` blob 的 protobuf 结构 |
| `apps/desktop/src/renderer/src/im-template/template/unreadDock.ts` | 把未读/高亮转成「跳转点」序列（纯函数） |

---

## 一、列结构

只有两列：

| 列 | 类型 | 含义 |
| -- | ---- | ---- |
| 48901 | TEXT | 会话键，格式 **`"chatType_uid"`**，如 `2_673646675`（群）、`1_u_xxxx`（好友） |
| 48902 | BLOB | 未读信息 protobuf，见下 |

> 注意 `48901`/`48902` 这对列号在 `nt_uid_mapping_table` 里是另一套含义（sortNo / uid）。
> QQ 的列号只在**表内**唯一，跨表复用很常见，不要按列号去猜语义。

查询就是一次主键命中：

```sql
SELECT "48901", "48902" FROM msg_unread_info_table WHERE "48901" = ? LIMIT 1;
-- 参数形如 "2_673646675"
```

## 二、未读数是算出来的，不是存出来的

**这张表里没有「未读数」这个字段。** 它只存「已读到的 seq」，未读数要自己减：

```text
未读数 = recent_contact_v3_table.40003 (会话最新消息 seq)
       - msg_unread_info_table.48902.41002 (已读到的 seq)
```

即需要**跨两张表**。WeQ 的做法（`MainView.tsx`）是先加载会话列表，
再按 12 个一批并发查每个会话的未读信息，两边相减；差值 ≤ 0 视作 0。

这个设计也解释了一个现象：未读数是「消息条数差」而不是精确的未读消息数 ——
中间若有被撤回/删除的消息，seq 仍然占位，所以红点数字可能比实际能看到的消息条数多。

## 三、`48902` 的结构

外壳只有一个 tag 同为 `48902` 的子消息。整体形状（已在真实 blob 上验证）：

```text
48902 (BLOB)
└── 48902 {
    ├── 40010  chatType             会话类型（与 48901 前缀重复）
    ├── 40021  peerUid              会话 uid（与 48901 后缀重复）
    ├── 41002  msgSeq               ★ 已读到的消息序号
    └── 50005 {                     会话扩展
        ├── 50001  peerUid          再重复一次
        ├── 50002  chatType         再重复一次
        └── 50060 {                 ★ 提醒高亮组（没有提醒时整块不存在）
            ├── 50000  kind         类别码，见第四节
            └── 50040 {             该类别下的高亮消息（可多条）
                ├── 50020  msgSeq
                ├── 50022  senderUid
                ├── 50023  sendTime
                └── 50024  text
            }
        }
    }
}
```

### 顶层字段

| tag | 字段名 | 类型 | 含义 | 置信度 |
| --- | ------ | ---- | ---- | ------ |
| 40010 | `chatType` | uint32 | 会话类型，同 `recent_contact_v3_table.40010` | 已验证 |
| 40021 | `peerUid` | string | 会话 uid | 已验证 |
| 41002 | `msgSeq` | uint32 | **已读到的消息序号** | 已验证 |
| 50005 | `ext` | message | 会话扩展，见下 | 已验证 |

另观测到 `41027` / `41032` / `41037` 三个计数类字段，语义未定，WeQ 未解析。

### 会话扩展（tag 50005）

| tag | 字段名 | 类型 | 含义 | 置信度 |
| --- | ------ | ---- | ---- | ------ |
| 50001 | `peerUid` | string | 会话 uid（重复 40021） | 已验证 |
| 50002 | `chatType` | uint32 | 会话类型（重复 40010） | 已验证 |
| 50060 | `highlight` | repeated message | **提醒高亮组**，见下 | 已验证 |

**普通会话的 `50005` 里只有 `50001` / `50002` 两个字段，没有 `50060`。**
所以判定很直接：`50060` 存在 ⇒ 这个会话有提醒类未读。

### 提醒高亮组（tag 50060）

| tag | 字段名 | 类型 | 含义 | 置信度 |
| --- | ------ | ---- | ---- | ------ |
| 50000 | `kind` | uint32 | **类别码**，见第四节 | 已验证 |
| 50040 | `items` | repeated message | 该类别下的高亮消息 | 已验证 |

**每个类别一个 `50060` 组**，壳子结构完全一样，只有 `50000` 的值不同。所以它被建模成 `repeated`。

### 高亮消息（tag 50040）

| tag | 字段名 | 类型 | 含义 | 置信度 |
| --- | ------ | ---- | ---- | ------ |
| 50020 | `msgSeq` | uint32 | 该条消息的序号 | 已验证 |
| 50022 | `senderUid` | string | 发送者 uid | 已验证 |
| 50023 | `sendTime` | uint32 | 发送时间，unix 秒 | 已验证 |
| 50024 | `text` | string | 预览文本，**实测常为空** | 观测一致 |

## 四、`50000` 类别码枚举

这是本页的重点。**这批码不是从 QQ 的枚举表抄来的**，QQ 前端不暴露它；
它是逐个触发场景、每次抓一份 blob 做 diff 逆向出来的 —— 同一个群（673646675）反复制造不同提醒，
观察到壳子完全不变、**只有 `50000` 的值在变**，于是把值和场景一一对上。

| 值 | 类别 | WeQ `HighlightKind` | 触发场景 | 置信度 |
| -- | ---- | ------------------- | -------- | ------ |
| 1000 | @我 | `atMe` | 群里有人 @ 我 | 已验证 |
| 1002 | 回复我 | `replyMe` | 群里有人回复我的消息 | 已验证 |
| 1006 | 特别关心 | `specialCare` | 被设为「特别关心」的好友/群友发来消息 | 已验证 |
| 1007 | QQ 红包 | `redPacket` | 会话内有未领取的红包 | 观测一致 |
| 2000 | @全体 | `atAll` | 群里有人 @全体成员 | 已验证 |
| 2001 | 新文件 | `newFile` | 群文件有新上传 | 已验证 |
| 2005 | 群公告 | `groupAnnouncement` | 群公告有更新 | 已验证 |
| 2006 | 群提醒词 | `groupKeyword` | 群里有人发出你设置的「关注词 / 提醒词」 | 已验证 |

未映射到的码会落到 `'unknown'`，同时保留 `rawKind` 原值，方便后续继续逆向。

补一个新类别的成本很低 —— 三处各加一行：
`HIGHLIGHT_KIND_BY_CODE`（db）、`ConversationHighlightKind`（前端类型）、`ConversationList` 的渲染分支。

> 数值本身也透着分组规律：`10xx` 像是「找我的」（@我 / 回复我 / 特别关心 / 红包），
> `20xx` 像是「群内广播」（@全体 / 新文件）。**未验证**，仅供继续逆向时参考。

## 五、展平约定

一个类别下可能有多条高亮消息（比如被 @ 了三次）。WeQ 每个类别只保留 **seq 最大的那一条**
（`extractHighlights`），因为界面只需要「有没有」这个布尔，`msgSeq` 保留但不展示。

结果对象：

```ts
interface UnreadHighlight {
  kind: HighlightKind;   // 映射后的类别
  rawKind: number;       // 50000 原值，未映射类别也能被识别
  msgSeq: number;        // 该类别下最新的一条
  senderUid: string;
  sendTime: number;
}
```

## 五之二、标记已读（`markRead`）

打开会话时 WeQ 会把未读/高亮「读进内存 → 标记已读」：

1. `getUnreadInfo()` 读出高亮与已读水位（这一步必须在清库**之前**，清完就没了）；
2. `markRead(chatType, uid, latestSeq?)` 把该会话标记为已读：
   - 把 `41002` 抬到会话最新 seq（`latestSeq`，缺省时从
     `recent_contact_v3_table.40003` 读）；
   - 删除**所有** `50060` 高亮组（它们在 `50005.ext` 里，可能有多组，要深度查找）。

**关键：写回走 wire 级编辑树，不能用 schema 重编码。** `48902` 里有大量 WeQ 还没
逆向的字段（`41024` 未读 seq 列表、`41027`/`41032`/`41037` 计数、`50006`/`50007` …），
用 `ProtoMsg(UnreadInfo).encode()` 重新序列化会把它们全丢掉（实测 405 字节 → 335 字节）。
所以 `markRead` 用 `@weq/codec/raw` 的 `buildEditTree` / `updateNode` / `removeNode` /
`encodeEditTree`：只改动 `41002` 与 `50060` 两条路径，其余节点**逐字节照抄原文**，
未解析字段原样保留（回归见 `packages/db/test/unread_info.test.ts`）。

幂等：已无高亮且 `41002 ≥ latestSeq` 时直接返回 `false`，不再写库。
静态账号（离线快照）在 IPC 层直接短路 —— 写进去 QQ 也不会读。

## 五之三、写入群提醒词高亮（`addHighlight`）

`markRead` 之外，还有一条**写**路径：`addHighlight(chatType, uid, hit)` 往 `50005 → 50060`
里追加一组高亮（`hit.kind` 原值，例如群关键词提醒用 `2006`）。它让 WeQ 自己产出的提醒
也能出现在会话列表的 `[群提醒词]` 角标，并且 QQ 客户端同样能读到。

关键点：

- 同样走 wire 级编辑树写回，未逆向字段逐字节保留；
- 已有**同类** `50060` 组时往它下面追加一条 `50040`，没有就新建组；
- 会话还没有 `48902` 行时，插一条只带 `chatType` / `peerUid` / 本次高亮的最小 blob；
- 幂等：同一 `(kind, msgSeq)` 重复写直接返回 `false`。

调用方是主进程的群关键词匹配器（见下节）：命中新到的群消息时弹系统通知卡（图标用群头像）
并调 `addHighlight`。**这条链路与 SSE 推送互相独立** —— SSE 推送地址没配 / 「实时消息」
关掉都不影响群提醒，因为匹配器有自己的 `nt_msg.db` 监听。

## 五之四、未读跳转坞（前端）

打开会话后，右上角会出现一串「跳转点」按钮，逐个引导用户跳转
（见 `unreadDock.ts`）：

1. **首屏可见就不跳**：第一条未读（`41002 + 1`）已落在首页 seq 范围内 ⇒ 整串不显示。
2. 否则把所有高亮（**不分类别**）混在一起按 seq 从大到小排，右上角**始终只显示一个**
   （最新的那条）；点掉它再显示下一个，依次类推。
3. 高亮跳完还有普通未读时，最后补一个「新的 N 条未读消息」，跳到最早那条未读。

跳转本身复用引用消息那套「快慢路径」（`jumpToSeq`）：目标在当前窗口内就直接滚
（快路径），在窗口外就重建以目标为中心的窗口（慢路径，恒定开销）。

**目标落在「空消息」上时不丢回原地**：跳转目标的 seq 可能没有对应行（被撤回 /
删除 / QQ 从未同步）。这时仍然把窗口定位过去、滚到最近的邻居，让相邻两行之间的
seq 缺口渲染出可点击的「此处有 N 条消息缺失 · 点击拉取」占位条，同时弹一条 Toast
说明。默认的缺口条只在跳空 > 1 时自动渲染；**恰好只缺这一条**（seq 差为 1）时，
由这次跳转在最近邻旁补一条同样的缺口条（见 `missingJumpSeq`），保证「跳到空消息」
永远有可点击的拉取入口。用户据此就能把消息拉下来 —— 引用消息跳转走的是同一套逻辑。

界面上分成两类颜色：**「找我的」告警类用红色**（`[特别关心]` / `[有人@我]` / `[@全体]` / `[有人回复我]` / `[群提醒词]`），
**内容类用蓝色**（`[新文件]` / `[群公告]`）。

## 六、和免打扰的关系：没有关系

一个容易走的弯路：免打扰状态**不在这张表里**。它在
[`recent_contact_v3_table` 的 `41220` 列](./recent-contact.md#会话设置与来源)。
这张表只管「读到哪了」和「有哪些提醒」，不管「要不要提醒」。
